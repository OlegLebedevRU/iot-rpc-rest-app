# Flow & Architecture: Device Collision Detection, Blocking & Audit

## 1. Введение и назначение

Данный документ описывает архитектуру и жизненный цикл подсистемы обнаружения коллизий идентификаторов устройств (дубликатов серийных номеров и клонированных накопителей), автоматической защиты брокера сообщений RabbitMQ, материализации состояния в БД и ведения единого журнала аудита жизненного цикла терминалов.

---

## 2. Классификация и дифференциация нарушений

В платформе Leo4 выделяются два принципиально разных типа сетевых аномалий:

```
                                  [Попытка подключения к RabbitMQ]
                                                 |
                       +-------------------------+-------------------------+
                       |                                                   |
           [Одинаковый SN, разные сертификаты]              [Одинаковый SN, одинаковый сертификат]
                       |                                                   |
                       v                                                   v
               SN_COLLISION_DETECTED                             DEVICE_CLONE_DETECTED
           (Мгновенная детекция: dt=0)                 (Многооконный фильтр: >= 3 conn, >= 2 IP)
```

### 1. `SN_COLLISION` (Дубликат серийного номера / Конфликт сертификатов)
- **Признаки**: Устройство подключается с тем же `SN` (`client_id`), но параметры TLS-сертификата клиента (`peer_cert_validity`, отпечаток) отличаются от параметров активной или предыдущей сессии.
- **Причина возникновения**: Выпуск нового сертификата на новое физическое оборудование без физического отключения или перепрошивки старого терминала.
- **Реакция детектора**: Мгновенная фиксация нарушения при первом обнаружении несовпадения сертификатов.

### 2. `DEVICE_CLONE` (Клон устройства / Клон накопителя)
- **Признаки**: `SN` и TLS-сертификат полностью идентичны, но устройство циклически инициирует сессии с разных публичных IP-адресов (`peer_host`), выбивая предыдущее соединение по протоколу MQTT (Takeover Flapping).
- **Причина возникновения**: Полное побитовое клонирование диска/образа операционной системы с приватным ключом на 2 и более физических терминала.
- **Защита от ложных срабатываний (False Positives Guardrail)**: 
  - В мобильных сетях (LTE/4G/3G) IP-адрес модема может периодически меняться при переключении вышек оператора.
  - Детектор использует многооконный скользящий анализ (окно 180 секунд): блокировка активируется только при наличии не менее 3 подключений с 2 и более различными IP-адресами и минимум 2 смен хостов ($IP_1 \to IP_2 \to IP_1$ или $IP_1 \to IP_2 \to IP_3$). Одиночная смена IP без повторного пинг-понга нарушением не считается.

## 3. Архитектурный цикл обработки инцидента

```
[RabbitMQ: amq.rabbitmq.event]
            |
            | connection.created
            v
[DeviceService.handle_connection_event]
            |
            | 1. evaluate_connection_collision()
            +------------------------------------+
            |                                    |
     [Нарушение найдено]                  [Всё в порядке]
            |                                    |
            v                                    v
 1. DeviceRepo.mark_device_blocked()      DeviceRepo.handle_connection_created()
    - is_blocked = True                   - last_checked_result = True
    - violation_type = ...                - update details & connected_at
    - violation_details = {...}
 2. tb_device_audit_logs INSERT (идемпотентно)
 3. RmqAdminApi.block_device_user()
    - PUT permissions: configure="", write="", read=""
    - DELETE topic-permissions
    - DELETE connections (принудительный килл активных сокетов)
```

## 4. Единый журнал аудита (`tb_device_audit_logs`)

Таблица `tb_device_audit_logs` объединяет все ключевые события жизненного цикла оборудования:
- `PROVISIONED`: Первичное создание или повторный перепровиженинг терминала.
- `DEVICE_CLONE`: Обнаружение и фиксация клона накопителя.
- `SN_COLLISION`: Обнаружение коллизии сертификатов.
- `BLOCKED`: Автоматическая или ручная блокировка доступа.
- `UNBLOCKED`: Снятие блокировки и восстановление прав.

### Защита от спама в аудит-логе
При продолжающихся попытках подключения заблокированных устройств (`is_blocked = True`) запись в аудит-лог создаётся **однократно** в момент первого перехода в состояние блокировки.

## 5. Процедура восстановления (Unblock & Reprovisioning)

Снятие блокировки и сброс сведений о нарушении производятся штатным образом через API провиженинга:

1. Вызов `POST /api/v1/internal/provisioning/terminals`.
2. `DeviceRepo.provision_terminals` в транзакции сбрасывает флаги:
   - `is_blocked = False`
   - `violation_type = None`
   - `violation_details = None`
3. В `tb_device_audit_logs` вносится запись `event_type = PROVISIONED`.
4. `RmqAdminApi.set_device_definitions` восстанавливает стандартные права доступа пользователя (`.*`, `.*`, `.*`) и топиков (`^dev.<SN>.*`, `^srv.<SN>.*`) в RabbitMQ.
5. In-memory история скользящего окна детектора для данного `SN` очищается.
