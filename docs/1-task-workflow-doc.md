# 📋 REST API · Задачи устройств

> Создать команду, отследить RPC-результат и прочитать историю. Базовый путь: `{base_url}/api/v1/device-tasks`.

[← REST API](rest-api.md) · [MQTT RPC](mqtt-rpc-protocol.md) · [Состояния](task_states.md) · [TTL](TTL.md)

## 🧭 Методы

| Метод | Путь | Ответ |
| :--- | :--- | :--- |
| `POST` | `/` | `200`: UUID задачи и время создания |
| `GET` | `/{id}` | `200`: заголовок, состояние, payload и результаты |
| `GET` | `/?device_id=4619&page=1&size=20` | Пагинированный список задач устройства |
| `DELETE` | `/{id}` | `200`: UUID и время soft delete |

Авторизация: `x-api-key: <organization-api-key>`. Устройство должно быть доступно организации ключа.

## ⚡ Создание · touch_task

```http
POST /api/v1/device-tasks/
x-api-key: <organization-api-key>
Content-Type: application/json
```

```json
{
  "ext_task_id": "open-cell-5",
  "device_id": 4619,
  "method_code": 51,
  "priority": 1,
  "ttl": 5,
  "payload": {"dt": [{"cl": 5}]}
}
```

```json
{
  "id": "5c75b4ed-2488-4769-b23a-2afae64ea22d",
  "created_at": 1791532800
}
```

| Поле | Правило |
| :--- | :--- |
| `ext_task_id` | Обязательная строка внешней системы; не заменяет UUID задачи |
| `device_id` | Обязательный числовой ID устройства |
| `method_code` | `0..65534`, по умолчанию `20`; поддержка определяется устройством |
| `priority` | `0..9`, по умолчанию `0`; большее значение выбирается раньше |
| `ttl` | `0..44639` минут, по умолчанию `1` |
| `payload` | JSON-объект или `null`; структура зависит от метода |

UUID генерирует IoT. `ext_task_id` не является ключом идемпотентности создания: повторный POST может создать ещё одну команду. Сохраняйте возвращённый UUID у себя.

Для `7000–7002` действуют валидаторы диагностики. `7003–7005` требуют ровно `{"dt":[]}`. `7011` требует один объект с `pin`, `pin_expires_at`, `ttl_sec=120`, без неизвестных полей; TTL должен быть положительным и не превышать оставшийся срок PIN. Подробности — [реестр методов](method-codes-reference.md).

## 🔍 Статус и результаты

```http
GET /api/v1/device-tasks/5c75b4ed-2488-4769-b23a-2afae64ea22d
x-api-key: <organization-api-key>
```

```json
{
  "id": "5c75b4ed-2488-4769-b23a-2afae64ea22d",
  "created_at": 1791532800,
  "header": {
    "ext_task_id": "open-cell-5",
    "device_id": 4619,
    "method_code": 51,
    "priority": 1,
    "ttl": 5
  },
  "status": 3,
  "pending_at": 1791532801,
  "locked_at": 1791532802,
  "payload": {"dt": [{"cl": 5}]},
  "results": [
    {"id": 304, "ext_id": 77, "status_code": 200, "result": {"status": "OK"}}
  ]
}
```

`created_at`, `pending_at` и `locked_at` в детальном ответе — Unix seconds; последние два могут быть `null`. `results` — массив: одна задача может иметь несколько логических результатов. В списке задач timestamps имеют формат datetime, поля заголовка находятся на верхнем уровне; `payload` и `results` в список не входят.

REST-история рекурсивно маскирует чувствительные поля в `payload` и `result`. Исходные параметры доставки доступны устройству через MQTT. Для renewal `7011` payload дополнительно очищается при результате, удалении и истечении.

> 📌 `DONE (3)` — сервер сохранил результат. Ошибка устройства, например `status_code=500`, также завершает активную задачу в `DONE`. Для открытия двери нужен факт `CellOpenEvent (13)` с подходящим тегом `304`, устройством и временем наблюдения.

## ⏱️ Срок и повторы

`ttl > 0` задаёт срок от создания задачи. Пока задача активна, GET/LIST показывают оставшиеся минуты с округлением вверх. `ttl=0` — короткая задача только для Trigger: адресная выборка доступна не более минуты; обычный polling её не выбирает.

Поздний RES сохраняется и получает CMT, но `EXPIRED` остаётся `EXPIRED`. Новый результат, принятый не позднее трёх минут после deadline, может создать обычный result webhook. Повторный RES не создаёт второй результат и webhook. Полные правила — [TTL](TTL.md).

## 🗑️ Удаление

DELETE выполняет soft delete и возвращает `{"id":"5c75b4ed-2488-4769-b23a-2afae64ea22d","deleted_at":1791532860}`. Задача скрывается из GET/LIST. Это не команда отмены уже начатого действия на устройстве: для отмены используйте соответствующий контракт агента.

После удаления поздний RES сохраняется и подтверждается CMT, сохраняя статус `DELETED`; новый webhook не создаётся.
