# IoT: tenant-изоляция и история пользовательских событий

Дата: 2026-10-01. Статус: реализовано, опубликовано и развёрнуто после команды
пользователя «деплой». Ветка `feature/l4mcp-event-history`, исходная база
`769d83e2bd02eb1d61c2e778957b1830a0463143` (`origin/master`).

## Результат

IoT сохраняет tenant каждого нового DevEvent по серверной DeviceOrgBind при
приёме. Payload и клиентское время не задают владельца; повтор события после
переноса устройства не меняет уже сохранённый org_id.

List, fields и incremental, включая public и internal API, требуют одновременно
текущую принадлежность устройства и совпадение сохранённого tenant события.
Строки с неизвестным владельцем остаются в БД, но исключены из этих API.
Это распространяется на все типы событий, а не только 900–999.

Новый GET `/api/internal/v1/device-events/search` читает события 900–999:
device_id, UUID448, список кодов, серверные временные границы, курсор ID и
limit до100. Он не изменяет общий offset. Полный контракт:
[internal API](internal-api-contract-v1.md).
Теги446–448 сохраняются внутри payload; existing DevEventOut не расширен.
UUID448 не заменяет MQTT correlationData и не является разрешением доступа.

## Миграция и выпуск

Миграция `0011_event_tenants` принадлежит IoT: nullable org_id и индекс
(org_id, device_id, id). Backfill отсутствует. Добавление индекса транзакционное,
с lock_timeout5s и statement_timeout120s: перед выпуском проверить объём
таблицы и допустимость блокировки. При превышении лимита миграция откатывается;
не увеличивать таймауты на production без оценки причины.

Старые строки станут недоступны tenant API после обновления приложения.
Строки от старого writer в переходный период также будут NULL и скрыты.
Откат образа совместим с расширенной схемой, но старый образ возвращает
прежний дефект изоляции чтения. Production downgrade с удалением org_id
не выполнять: он уничтожает сведения о владельце новых событий.

Предлагаемый путь: принять проверенный SHA в origin/master, затем чистый
checkout на выделенном builder, `deploy/registry_app1.py`, private registry
и immutable digest. Production получает digest через общий deployer;
пересоздаётся только app1 с no-deps/no-build/pull-never, миграция выполняется
prestart. Подробности: [runbook §0](manual-app1-deploy-runbook.md#0-production-единый-порядок-доставки).
Первоначально пользователь потребовал остановку перед деплоем; выпуск
выполнен только после отдельного решения «деплой».

## Следующие стеки

MenuBuilder должен передавать effective tenant из своей авторизации через
internal интеграцию; пользователь не задаёт X-Org-Id. Затем l4mcp добавляет
чтение истории и запуск с UUID448 в существующем console flow. Они в этой
реализации не изменены. Источник истории — основная БД; tenant-safe архив
и восстановление принадлежности старой истории относятся к отдельному этапу.
