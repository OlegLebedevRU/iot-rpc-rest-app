# 📨 REST API · История событий

> Чтение сохранённых фактов, инкрементальный поток и выборка значений тегов.

[← REST API](rest-api.md) · [События MQTT](event-protocol-mqtt.md) · [Типы](event-types-reference.md) · [Webhooks](3-webhooks.md)

Базовый путь: `{base_url}/api/v1/device-events`. Авторизация: `x-api-key: <organization-api-key>`.

## 🧭 Выберите способ чтения

| Задача | Метод | Формат ответа |
| :--- | :--- | :--- |
| Просмотреть историю устройства | `GET /?device_id=4619` | Страница `items/total/page/size/pages` |
| Получить новые записи | `GET /incremental?device_id=4619&last_event_id=800&limit=50` | Массив событий |
| Найти значение свойства | `GET /fields/?device_id=4619&event_type_code=13&tag=304&interval_m=5&limit=10` | Массив `created_at/value/interval_sec` |

Доступны события, записанные за организацией читателя и относящиеся к устройствам, доступным ей сейчас. Перепривязка устройства не делает прежнюю историю другой организации доступной новому владельцу.

## 📦 Объект DevEventOut

```json
{
  "id": 801,
  "device_id": 4619,
  "event_type_code": 13,
  "dev_event_id": 20338,
  "created_at": "2026-10-09T08:00:01Z",
  "dev_timestamp": "2026-10-09T08:00:00Z",
  "payload": {
    "101": 20338,
    "102": "2026-10-09T08:00:00Z",
    "200": 13,
    "300": [{"304": 5}]
  }
}
```

| Поле | Значение |
| :--- | :--- |
| `id` | Серверный ID записи; используйте как cursor |
| `device_id` | ID устройства в IoT |
| `event_type_code` | Код из transport metadata |
| `dev_event_id` | ID публикации на устройстве |
| `created_at` | Время сохранения сервером |
| `dev_timestamp` | Время устройства, разобранное из header, либо серверное fallback-время |
| `payload` | Исходная JSON-структура события, без переименования тегов |

`payload` сохраняет JSON-значения, а не исходные байты и форматирование MQTT-сообщения. `dev_event_id` и `id` имеют разные пространства идентификаторов.

## 🗂️ История с пагинацией

```http
GET /api/v1/device-events/?device_id=4619&events_include=13&events_include=14&page=1&size=20
x-api-key: <organization-api-key>
```

`device_id` обязателен. Списки `events_include` и `events_exclude` передаются повторяющимися query-параметрами. Ответ использует стандартную страницу. Фильтры диапазона дат и `event_type_code` как одиночный параметр для этого публичного метода не объявлены.

## 🔄 Инкрементальное чтение

| Параметр | Правило |
| :--- | :--- |
| `device_id` | Необязателен: без него чтение по доступным устройствам организации |
| `last_event_id` | Вернуть записи с серверным `id` больше указанного |
| `limit` | `1..100`, по умолчанию `50` |

Порядок — `id ASC`. Без `last_event_id` сервер читает после сохранённого offset каждого устройства; если offset отсутствует, используется `0`. После непустой выдачи offset обновляется **даже при явном last_event_id**. Это общий серверный offset устройства, поэтому независимым потребителям следует хранить собственные cursors и всегда передавать их явно.

Сохраните максимальный `id` успешно обработанной порции. Пустой массив означает отсутствие новых доступных записей. Повторы обработки на клиенте устраняйте по серверному `id`.

## 🏷️ Значения тега · fields

Метод извлекает тег из **первого** объекта `payload["300"][0]`; если значение отсутствует, использует одноимённое поле верхнего уровня. Остальные объекты массива этим методом не просматриваются.

| Параметр | Значение по умолчанию и границы |
| :--- | :--- |
| `device_id` | Обязательный |
| `event_type_code` | `44`, диапазон `0..65534` |
| `tag` | `338`, диапазон `0..65534` |
| `interval_m` | `15`, диапазон `1..3599` минут от текущего серверного времени |
| `limit` | `50`, диапазон `1..100` |

```json
[
  {"created_at":"2026-10-09T08:00:01Z","value":5,"interval_sec":4}
]
```

Порядок — от новых к старым. `interval_sec` — возраст записи относительно времени запроса. `value` сохраняет JSON-тип и может быть `null`.

Для подтверждения открытия проверяйте код `13`, нужную ячейку и время после начала сценария. Старое открытие той же ячейки не подтверждает новую команду. Когда устройством не передан ID исходной операции, совпадение по времени и ячейке не обеспечивает строгую причинную корреляцию.

## 📊 Что не входит в историю

Gauge `44` по умолчанию обновляет текущий снимок и не создаёт запись события; читайте `/api/v1/gauges/`. Служебные `75/76` и пользовательские `900–999` сохраняются как обычные события. Маркированный Channel Probe в историю не входит.

Для независимого поиска пользовательских событий `900–999` существует **внутренний** `GET /api/internal/v1/device-events/search`: фильтры по внешнему UUID `448`, кодам, времени и cursor; он не изменяет offsets. Это отдельный [межсервисный контракт](user-event-history-iot-handoff.md), без публичного аналога `/api/v1/device-events/search`.
