# RPC: решения и состояние реализации на 29 сентября 2026

Документ фиксирует исследование и согласованный рефакторинг. Канонические правила:
[TTL](../TTL.md), [MQTT RPC](../mqtt-rpc-protocol.md),
[состояния задач](../task_states.md). Изменения подготовлены в рабочем дереве;
миграция и приложение на сервере не развёрнуты.

## Архитектурное решение

PostgreSQL остаётся источником истины для задачи, её срока действия и результатов.
Redis обслуживает временное инфраструктурное состояние; перенос RPC-задач,
результатов или дедлайнов в Redis не требуется. Потеря либо вытеснение ключа Redis
не должны изменять решение о принятии результата или об истечении задачи.

Ранее срок жизни определялся изменением счётчика TTL периодическими заданиями.
Повторный запуск мог повторно уменьшать TTL; задержки и общий сохранённый момент
запуска связывали срок отдельных задач с работой планировщика. Теперь у каждой
задачи есть `expires_at`. Задание только переводит просроченные активные задачи
в `EXPIRED`; REQ и ACK проверяют дедлайн независимо от этого задания.

Сохранение нового результата и изменение состояния задачи выполняются одной
транзакцией. RES блокирует сначала задачу, затем строку её состояния. DELETE
использует тот же порядок. Это сериализует конкурирующие результаты одной задачи
и исключает восстановление удалённой задачи через RES. Поздний ACK не возвращает
LOCK или терминальные состояния в PENDING. Адресные REQ, ACK и RES проверяют SN.

## Согласованные контракты

| Ситуация | Поведение |
|---|---|
| `ttl > 0` | Дедлайн от создания; внешний TTL в минутах, остаток округляется вверх |
| `ttl=0` | Только trigger по UUID, внутреннее окно до минуты от создания; внешний TTL всегда `0` |
| Polling | Исключает trigger-only и просроченные задачи; повторный LOCK допустим; порядок priority DESC, остаток TTL ASC, created_at ASC |
| Новый RES после EXPIRED | Сохранение и CMT, состояние остаётся EXPIRED |
| Webhook после EXPIRED | Только для нового результата, принятого не позднее expires_at + 3 минуты, включая границу |
| RES после DELETE | Сохранение и CMT, без webhook; состояние остаётся DELETED |
| Валидный `result_uid` | UUID в MQTT User Property; ключ дедупликации — task_id + result_uid |
| UID отсутствует или невалиден | Legacy-ключ: task_id + ext_id + status_code + нормализованный JSON |
| Повтор или конфликт UID | Первый результат сохраняется, возвращается прежний result_id/ext_id; новой записи, webhook и повторного начисления нет; конфликт пишется в лог |
| `status_code` | Приоритет заголовка, прежний default 501; поле payload не подменяет заголовок |

Новые устройства обязаны сохранять один `result_uid` при повторной передаче
одного логического результата. Автоматического объединения результатов с UID и
без UID нет. Неоднозначность legacy-ключа принята: два логически разных, но
одинаковых результата без UID различить невозможно. DONE по-прежнему не означает
физическое выполнение команды.

Публичные поля REST и тела сообщений не расширены внутренними дедлайнами.
`result_uid` добавлен совместимым заголовком. Топики, correlation data и лимиты
method_code сохранены. AMQP expiration исправлен: библиотеке передаются секунды
или timedelta, а не миллисекунды как число секунд.

## Что показала БД

В исследованном снимке было 790 задач и 722 результата. Найдены 52 пары
одинаковых результатов метода 7002; у 712 результатов ext_id равен нулю.
У пяти задач одинаковый ext_id сопровождался разными кодами или телами результата:
одного ext_id недостаточно для дедупликации. У 362 результатов сохранённый код 501
сочетался с payload status_code 200. Это подтверждает необходимость явно
документировать источник status_code, но не даёт основания менять старые данные.

Исторические записи не удаляются и не перенумеровываются. Legacy-поиск учитывает
старые результаты без нового fingerprint. У старых EXPIRED нет достоверного
момента истечения: миграция оставляет expires_at NULL, а поздний RES сохраняет
без создания webhook. Активным задачам с положительным TTL миграция переносит
оставшиеся минуты от момента миграции; нулевым — минутное окно от создания.

## План улучшения и проверки

1. **Подготовлено:** дедлайны вместо декремента, атомарное сохранение RES и
   состояния, проверка владельца, защита ACK, дедупликация, правила позднего RES,
   совместимые заголовки, исправление транспортного expiration и документация.
   Добавлены миграции `0009_rpc_task_deadlines` и `0010_rpc_result_webhooks` после
   уже работающей на проде `0008_org_reservations`; индексы отражены также в ORM.
2. **Проверено на сборщике 176.108.247.249:** миграции на изолированном PostgreSQL 18
   со старой структурой и синтетическими данными; восемь конкурентных RES,
   гонка RES/DELETE, обе стороны границы expires_at + 3 минуты, повторный запуск
   expiration, сохранение legacy-результатов, конкурентные воркеры доставки и
   продолжение сохранённого retry в новой сессии. Проверка выполняется отдельным
   opt-in тестом `test_rpc_postgres_integration.py`, без отправки HTTP наружу.
3. **Развёртывание отдельным действием:** резервная копия, остановка старых
   процессов записи RPC/TTL, применение миграции, запуск совместимой версии и
   проверки REQ/ACK/RES. Смешанный запуск старых и новых writers не поддерживается:
   старые процессы не заполняют новые обязательные поля и не соблюдают дедупликацию.
   Инфраструктурные контейнеры пересоздавать не требуется. При откате TTL активных
   задач пересчитывается из дедлайнов в downgrade перед возвратом старого приложения.
4. **Реализовано после уточнения требований:** небольшая таблица доставок RPC,
   заполняемая в транзакции RES. Фоновый обработчик отправляет HTTP существующим
   клиентом, сохраняет нарастающие ретраи и итог. Промежуточная AMQP-публикация для
   новых результатов больше не нужна. Подробности: [доставка webhook](../3-webhooks.md).

## Существенные ограничения

Намерение доставки webhook теперь переживает аварии после commit RES и не зависит
от CMT. Удалённый HTTP-получатель всё ещё может обработать запрос без успешного
ответа серверу. Поэтому HTTP-повторы возможны, а получателю необходима
дедупликация по x-result-id. Число попыток и срок доставки ограничены; гарантия
exactly-once не заявляется. Дедупликация RES не создаёт дополнительной доставки.

Redis с политикой volatile-lru может вытеснять lease до его TTL. Допустимое число
сессий следует оценивать по измеренному размеру ключей, базовому потреблению и
резерву памяти, а не по выдуманному фиксированному лимиту; методика добавлена в
[руководство Redis](../redis/redis-integration-guide.md).

Дополнительно исправлен воспроизводимый дефект запроса DELETE: отсутствовал
явный FROM для проверки доступа, из-за чего SQLAlchemy отклонял запрос до
отправки в БД. Проверка компиляции SQL теперь входит в тесты жизненного цикла.
