# IoT: единая база master

## Решение владельца

Репозиторий используется только текущим проектом и его production-деплоем.
Базовая ветка — **master**. Новые задачи начинаются от актуального
`origin/master`; завершённые ветки каскада являются историей приёмки.

До консолидации master находилась на `fcc67ef`, на 41 коммит позади принятой
18C. Fast-forward до `a31025b7236830533567a49ab15b4259a7bd76ca` сохраняет
всю историю, исходные SHA и ссылки из handoff. Конфликтов и нового объединения
runtime-кода нет. Последующие изменения этой задачи — только документация.

Временная локальная main удалена после выбора владельцем master;
удалённая main не создавалась. Default branch GitHub остаётся master.

- Центральная приёмка 18C: `5d2f23cf54b3b39e47405bf9bb7bc6df3a7e96f7`.

Source и image повторно сверены на production read-only. Развёрнутый source
является предком новой master; app-service, Dockerfile, lockfile и контракты
архива совпадают с принятой версией. В этой задаче контейнер не пересобирается
и не перезапускается. Сервер сохраняет detached checkout точного release SHA.

Неперенесённых runtime-исправлений в этих вершинах не обнаружено. Исторические
ветки сохранены: их массовое удаление не требуется для смены базы и может
затронуть ссылки старых handoff. Для текущей работы использовать master,
а не выбирать одну из старых веток по имени или времени коммита.

## Локальные рабочие деревья

Чистое дерево для master: `iot-rpc-rest-app-master` рядом с остальными
рабочими деревьями. В исходном `iot-rpc-rest-app` остались четыре изменённых
schema JSON и untracked `.notes/`. Также существует stash
`l4d prompts WIP before 17C`. Эти локальные данные не удалены и не объявлены
релизными изменениями; они не мешают работе из чистой master.

## Дальнейший процесс

```bash
git fetch origin
git switch master
git pull --ff-only origin master
git switch -c fix/short-task-name
```

После проверок объединять задачу в master. Для деплоя выбирать полный SHA,
проверять образ, schema и rollback по runbook. Принятые отчёты и candidate
не переписывать; новые изменения оформлять новой задачей/веткой.

Проверка консолидации: ancestry старой master и release source, отсутствие
runtime diff относительно принятого source, публикация master без force push
и совпадение локального/удалённого HEAD. Нового runtime-кода нет, поэтому
повтор тестов принятой 18C не нужен; результаты остаются в её отчёте.
