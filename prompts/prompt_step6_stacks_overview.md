# Шаг 6 — Предсказуемая установка и безопасная работа standalone-киоска, tools v1.7.2

## 1. Статус, цель и границы

- **Статус:** требования после архитектурной ревизии; реализация и стендовая приемка не подтверждены.
- **Цель:** один понятный запуск `l4setup` до комплекта проверенных, автоматически стартующих служб; затем работа без локального администратора, UAC, неожиданных окон, выхода из сеанса и самовольной перезагрузки.
- **Версия пакета:** `1.7.2`. Этот комплект описывает будущие работы, а не разрешает немедленную публикацию или вмешательство в рабочие терминалы.
- **Минимальный подход:** Win32/SCM, один последовательный установочный процесс, существующие механизмы контроля процессов и протоколы. Не создавать универсальный workflow engine, новый сервис повышения прав или второй watchdog.
- Все задания читаются вместе с этим обзором. Здесь — общие инварианты и контракты, в заданиях — детали реализации и проверок. При расхождении с действующим кодом/правилами агент фиксирует конфликт и согласует его, а не выбирает удобную трактовку.

### Что исправляет ревизия

| Риск исходного комплекта | Решение |
|---|---|
| `TokenLinkedToken` якобы всегда дает High IL | Проверять тип, IL и сессию токена; обычного пользователя нельзя таким способом превратить в администратора |
| Проверка классов окон якобы исключает Winlogon | Запрет опасных действий по умолчанию; проверка input desktop и сессии; никаких обещаний предсказать поведение произвольного приложения |
| `--silent` якобы единственный автономный режим | Повышение прав никогда не инициируется программой; GUI только по явному выбору обслуживающего человека |
| 30 секунд, затем необходимость срочно нажать Retry | 30 секунд — уведомление, ожидание автоматически продолжается с конечным пределом; UI не блокируется |
| `SERVICE_RUNNING` и совпадение версии означают готовность | Отдельные проверки локальной работоспособности, активации и связи; честный итог |
| Принудительный kill и «атомарная» замена каталога файлов | Подготовка до остановки, контроль владения, резервная копия, восстановление без перезагрузки |
| Сначала публикация, потом стенд | Сборка кандидата → приемка этих байтов → публикация → проверка скачанного пакета |

## 2. Общие инварианты безопасности

### 2.1. Установка с человеком и автономный запуск — разные сценарии

- По умолчанию любой запуск `l4setup` неинтерактивный и **никогда не повышает себя**. Явный `--interactive` включает GUI для первичной установки/обслуживания с присутствующим человеком; `--silent` исключает все окна. Эти режимы взаимоисключающие; ошибочные аргументы дают отказ без GUI.
- В обоих режимах административные права должны быть предоставлены **до** запуска установочного процесса. Манифест установщика — `asInvoker`, `uiAccess="false"`; нет `requireAdministrator`, `highestAvailable` и автоперезапуска через `runas`.
- Во время первичной подготовки человек может сам открыть повышенный процесс штатными средствами Windows. Возможный UAC на этом этапе — осознанное действие человека, а не скрытая часть автоматизации. Для автономного обслуживания запуск производится уже установленным доверенным механизмом с достаточными правами.
- При недостатке прав установочная операция возвращает **exit code `20`** без окон, PIN-диалога и изменений. Это код продукта, **не** Win32 `ERROR_ACCESS_DENIED` (тот равен `5`). `--help` и `--version` работают без повышения.
- Наличие вошедшего пользователя, интерактивного desktop, TTY или отсутствие `--silent` не доказывает присутствие обслуживающего человека. `--interactive` вне доступной локальной сессии обслуживания отклоняется, а не оставляет скрытый диалог в Session 0.
- После первичного старта ни служба, ни агент, ни обновление не вызывает `runas`, UAC/credential UI, `LockWorkStation`, logoff, SAS, переключение desktop, автоматический reboot/shutdown. Не отключать UAC, secure desktop, Defender, SmartScreen или Windows Update ради выполнения этого требования.
- Ошибки запуска/crash собственных процессов и помощников не открывают Windows Error Reporting, critical-error или консольные окна: использовать штатный error mode в области этих процессов и неблокирующую диагностику в лог. Не отключать системную отчетность глобально и не скрывать сам факт сбоя.
- Не менять autologon, учетные записи, пароль, shell, screensaver и политики блокировки автоматически. Это предварительно подготовленный и проверенный образ киоска. Недостатки образа — явный результат preflight, а не повод экспериментировать на удаленном терминале.
- Политики сна, уведомлений и планового обслуживания Windows также проверяются в образе: комплект не может гарантировать отсутствие экранов, инициированных ОС, сторонним приложением или оператором вне его контроля.

### 2.2. Права и рабочая сессия

- `l4superv` остается доверенной службой LocalSystem; `l4desk` — процессом **пользователя целевой консольной сессии**, не SYSTEM-процессом на пользовательском desktop. Запуск только в `winsta0\default`, не в Session 0, не в произвольно выбранной RDP-сессии.
- Предпочтителен одинаковый минимально достаточный IL приложения киоска и агента. Если существующему киоску нужен High IL, допускается проверенный полный токен того же пользователя; не повышать учетную запись и не добывать токен чужого процесса.
- `TokenElevationTypeLimited`: запросить связанный токен и проверить, что он действительно повышенный, нужного пользователя и сессии. `Full`: не заменять его связанным ограниченным токеном. `Default`: связанного токена нет, проверить фактические права/IL. Нет подходящего токена — `insufficient_integrity`, без UAC и без выдачи неработающего ввода за успешный запуск.
- При отсутствии входа, блокировке или отключении целевой сессии службы продолжают работать; ввод недоступен. Не выполнять автоматический вход/разблокировку. После восстановления сессии нужны актуальные lease и эпоха потока; старые команды не воспроизводятся.
- Исполняемые файлы, конфигурация высокопривилегированных компонентов, SCM и локальный управляющий IPC защищены ACL от записи непривилегированными пользователями. Абсолютные пути, контролируемый рабочий каталог, никаких командных строк/путей из сетевого payload для привилегированного запуска.

### 2.3. Границы гарантии «без UAC и Winlogon»

- High IL снимает только соответствующее ограничение UIPI для ввода в окна равного/меньшего IL. Это не доступ к secure desktop, другим сессиям, защищенному видео или любому окну SYSTEM.
- Проверка `GetForegroundWindow` не может предсказать, откроет ли приложение UAC, завершит ли shell/сеанс, и не устраняет гонку смены фокуса. `SendInput` не адресуется конкретному HWND.
- Поэтому `alt_f4` и `win_d` **запрещены по умолчанию на рабочем киоске**. `f12` разрешается только для проверенного сценария приложения. Не превращать быстрые кнопки в способ выхода из киоска.
- Допуск опасных шорткатов возможен только как отдельно разрешенное обслуживание проверенного образа/приложений. Терминальная политика хранится локально с защищенными ACL; браузер не может ее ослабить. Если безопасный профиль не подтвержден, действие остается запрещенным.
- Те же ограничения действуют на обычные `key_event` и сочетания: нельзя обойти запрет кнопки последовательностью клавиш. Произвольная мышь/клавиатура над произвольными программами не дает абсолютной гарантии отсутствия системных диалогов. Для строгого автономного профиля доступные приложения/действия ограничиваются образом киоска; такую гарантию не подменять фильтром имен окон.

## 4. Единый контракт удаленного ввода

Существующая цепочка: UI → MenuBuilder BFF → `app1` → `srv/{SN}/ctl`; ответы — `dev/{SN}/ctl` → `app1` → UI. Сохранить действующие envelopes, корреляцию и коды; следующие payload — требования к расширению после согласования, не новая параллельная шина.

### 4.1. Команды

```json
{
  "v": 1,
  "type": "mouse_click",
  "command_id": "<uuid-v4>",
  "lease_id": "<uuid-v4>",
  "sn": "<SN>",
  "source_id": "disp:<id>",
  "stream_instance_id": "<uuid-v4>",
  "button": "right",
  "x": 32768,
  "y": 32768,
  "expires_at_ms": 1789367400000
}
```

- `button`: `left` или `right`; отсутствие означает `left`. `middle` не включать в публичное расширение шага 6, даже если локальная функция его уже поддерживает. Неизвестные значения отклонять, а не превращать в левый клик.
- `x`, `y`: целые `0..65535`, координаты реальной области desktop без полос видео. `expires_at_ms` в примере условный; отправитель вычисляет действительный короткий срок по текущему времени.
- `shortcut_action` имеет тот же envelope, вместо `button/x/y` — `action`: ровно одно из `f12`, `alt_f4`, `win_d`.
- UI посылает только тип действия, параметры и `client_ref`; доверенные SN, owner, scope, `command_id`, lease и эпоху формирует/проверяет сервер. `client_ref` не заменяет `command_id`.

### 4.2. Исполнение и результат

1. Проверить права на устройство/организацию, активную lease со scope `input`, desktop stream, SN, source, эпоху, TTL, дедупликацию и локальную политику. Проверки обязательны и на доверенной серверной границе, и в пределах имеющегося локального состояния терминала.
2. Команды и ACK/NACK — без retain. Доставка QoS 1 допускает дубликаты: повторный `command_id` не выполняет действие второй раз. На reconnect/timeout не повторять клики или шорткаты автоматически, не ставить их в очередь для будущей сессии.
3. До ввода проверить состояние целевой сессии и **input desktop** через `OpenInputDesktop`/`GetUserObjectInformationW`; ошибка проверки означает запрет. `GetThreadDesktop` не подтверждает, какой desktop получает ввод.
4. Мышь: `MOVE + DOWN` → пауза 40 мс → `UP`. Клавиши: down → 40 мс → up; модификаторы отпускаются в обратном порядке. Проверять число вставленных событий, сериализовать ввод, освобождать только собственные нажатия при ошибке/потере lease. Не блокировать MQTT keepalive ожиданием клика.
5. `alt_f4`: помимо запрета по умолчанию блокировать shell, основной процесс киоска, неизвестную цель и смену фокуса. Классы `Progman`, `WorkerW`, `Shell_TrayWnd`, `Shell_SecondaryTrayWnd` — дополнительный deny-list, не доказательство безопасности остальных окон. Не заменять Alt+F4 на `WM_CLOSE`, kill или logout.
6. `injected` означает только принятие полного набора событий Windows, **не** закрытие приложения/появление меню. Частичное выполнение — ошибка с неопределенным эффектом, без повтора. Причину UIPI нельзя достоверно вывести только из `GetLastError`.

Семантика причин (сопоставить с существующей схемой ACK/NACK, не менять envelope несогласованно):

| Причина | Значение |
|---|---|
| `desktop_locked` | Input desktop недоступен/не default, ввод запрещен |
| `session_unavailable` | Нет подходящей активной консольной сессии |
| `insufficient_integrity` | Нет достаточного IL для выбранного профиля |
| `action_blocked_policy` | Действие запрещено политикой киоска |
| `action_blocked_winlogon_guard` | Shell, защищенная/неизвестная цель или смена фокуса |
| `input_injection_failed` | Windows не приняла весь ввод; эффект не подтвержден |

Пример содержимого NACK: `{"result":"nack","code":"action_blocked_policy","message":"Action is disabled on this kiosk"}`. Сохранить обязательные поля корреляции полного ответа. Не логировать PIN, ключи, JWT, полный чувствительный payload или содержимое клавиатурного ввода.

## 5. Единый контракт setup и готовности

- Один GUI с фазами **Check → Prepare → Stop → Update → Start → Verify → Finish**; один worker и обычный Win32 message loop. Не отдельный мастер для каждой службы.
- До `Install / Upgrade / Repair` человек видит текущую/целевую версии, изменения, ожидаемый перерыв связи, права, активацию и путь лога. После подтверждения исправный сценарий проходит до конца без дополнительных кликов. Нет автонажатий, countdown, автоматического закрытия итога или требования уложиться в две секунды.
- Все собственные тексты setup — английские; Win32 Unicode API обязательны и для не-ASCII путей. PIN — шесть цифр, не в логах; `Skip activation` явно означает неполную установку, не `ready`.
- Порядок служб по подтвержденным зависимостям: `Leo4Proxy → mosquitto → L4Con → L4Superv`; останов — обратный. Агент 3 проверяет реальные зависимости SCM/приложений, прежде чем закреплять порядок.
- Ожидание одной службы: на 30 с показать `Taking longer than usual; still waiting...`, автоматически продолжать до **120 с** с учетом `dwCheckPoint`/`dwWaitHint` и абсолютного монотонного deadline. Опрос ограничен, без busy loop. Полный проход запуска четырех служб ≤ **480 с**; дополнительные health/network probes имеют отдельный отображаемый лимит **60 с на проход**.
- После предела: `Retry`, `View details`, `Cancel`. `Retry` сначала перечитывает состояние; не делает restart здоровой службы и не вызывает `StartService` повторно в `START_PENDING`. Нет `Continue` с ложным успехом. В unattended нет вопросов и бесконечных повторов, только ограниченный проход, отчет и ненулевой код.
- `SERVICE_RUNNING` — лишь состояние SCM. Для каждой службы нужны безопасные локальные probes, валидный сертификат/доступ к ключу и отдельный результат внешней связи. Не начинать тестовую платежную операцию для проверки готовности.
- `state.json.installed_version` фиксирует установленный и локально проверенный набор бинарников. Записывать атомарно после локальной проверки; совпадение строки не заменяет сверку бинарников, конфигурации и здоровья. Поврежденное/незавершенное состояние сначала сверяется с реальностью.
- `install_summary.json`: версия установщика и установленного набора, итог `ready` / `activation_required` / `degraded` / `failed` / `cancelled`, фаза/причина, статусы четырех служб и probes, связь, доступность remote input, результат восстановления, путь лога; никаких секретов. Отдельно показывать «службы запущены» и «удаленный ввод доступен».
- **Exit `0` только для `ready`**: четыре обязательные службы локально работоспособны, активация и проверяемый канал управления подтверждены. Нет пользовательского входа — допустимо для комплекта служб, но `remote_input=session_unavailable` явно виден, не обещать рабочий desktop. При потере сети — `degraded`, службы остаются запущенными; не откатывать исправные файлы из-за недоступного сервера.
- Exit `20` — недостаток прав. Остальные неуспешные состояния получают стабильные ненулевые коды из существующего CLI; агент 3 до реализации фиксирует итоговую таблицу и передает агенту 5. Не переиспользовать `0` для skip/cancel/timeout.
- Upgrade/repair: один экземпляр установки, подготовка и проверка payload **до** остановки, резерв только заменяемых файлов/конфигурации, контролируемая замена и ограниченное восстановление. Никакого `taskkill /IM`, перезапуска Windows для освобождения файлов или автоматического downgrade. Повтор исправной установки не перезаписывает бинарники/конфигурацию, не перевыпускает сертификат и не перезапускает службы.
- После выхода setup запуском служб владеет SCM, процессом l4desk — l4superv, FFmpeg — его существующий владелец. Ограниченное recovery с задержками, без restart storm, окон и самопроизвольного обновления. Boot/logout/network-loss/crash проверяются отдельно на стенде.
