# Задание 4 (Шаг 6): tools v1.7.2 — Кандидат, приемка, затем публикация

## 1. Роль, scope и два этапа

Ты Windows Release Engineer. Обязателен [обзор шага 6](prompt_step6_stacks_overview.md). Работай с `tools\build_dist.cmd`, версиями/ресурсами компонентов, `tools\dist`, `deploy\publish_l4tools.py`, `artifacts\l4tools\1.7.2.json` и `releases.jsonl`.

- **4A:** собрать локальный кандидат после завершения заданий 1, 2A (app1), 2B (MenuBuilder), 3 и передать байты/хеши агенту 5. Серверный/UI код не включается в Windows-пакет; его совместимые ревизии фиксируются для стенда.
- **4B:** только после успешной 5A и явного разрешения на публикацию доставить **тот же** кандидат в Generic-реестр и передать его на 5B.
- До 5A ничего не публиковать. Этот промпт не разрешает массовую установку на киоски, изменение production-сервисов или немедленный auto-update терминалов.
- Изменился код, payload или манифест после приемки — это другой кандидат, нужна повторная соответствующая проверка. Не считать rebuild с тем же номером версии эквивалентом испытанных байтов.

## 2. Этап 4A — Подготовка и сборка

### 2.1. Preflight

1. Получить от агентов 1, 2A, 2B, 3 результаты тестов, список поддерживаемых профилей/OS, схемы и ограничения, CLI modes/exit codes, фактические health checks и recovery limits. По заданию 2 обязательны оба результата: контракт app1 из 2A и интеграция MenuBuilder из 2B; не считать отсутствующий `app1` или непроверенную цепочку готовыми.
2. Проверить Git-состояние и состав собираемых исходников. Не включать посторонние изменения автоматически и не сбрасывать чужую работу. Зафиксировать реальную ревизию; недопустимо приписывать dirty-сборку чистому `git_sha` без описания отличий.
3. Версия строго `1.7.2`. Проверить локальную схему ресурсов/манифеста и реестр перед будущей публикацией: занятый номер версии нельзя молча перезаписывать или менять на другой.
4. Согласовать матрицу OS/архитектур со всем payload: сборка x86 не доказывает поддержку Windows 7/POSReady 7. Не копировать `min_os: "6.1"`, версии FFmpeg/mosquitto/Leo4Proxy из старого примера без доказательств. Если заявленная проектом совместимость не подтверждается зависимостью — блокировать релиз и согласовать решение, не сужать поддержку молча.

### 2.2. Сборка и локальная проверка

- Синхронизировать версии `l4setup`, `l4superv`, `l4desk`, `l4con`, `l4pin`: version headers, `.rc`, строковые значения и PE `1.7.2.0` по существующей схеме. Не менять несвязанные версии зависимостей.
- Выполнить штатный конвейер из корня проекта:

```powershell
cmd /c "tools\build_dist.cmd 1.7.2"
```

- Собрать x86/x64 `/MT`, проверить архитектуры PE и соответствие содержимого встроенных payload. Не использовать оставшиеся бинарники от старой сборки. Финальный `tools\dist\l4setup.exe` должен содержать правильные payload обеих архитектур.
- Проверить **встроенные** манифесты установщика и l4desk: `asInvoker`, `uiAccess="false"`; отсутствие неявного elevation в помощниках. Запуск `--version` не должен требовать прав:

```powershell
.\tools\dist\l4setup.exe --version
Get-FileHash -Algorithm SHA256 -LiteralPath .\tools\dist\l4setup.exe
```

- `--version` сообщает `1.7.2`; не привязывать проверку к рекламному названию вроде Zero-Touch, если реальный CLI использует другой текст.
- Сгенерировать `l4tools-release.json` по **существующей** схеме: версия, реальная ревизия исходников, UTC-время сборки, файлы с размером и SHA-256, фактические версии компонентов, проверенные OS/архитектуры. Изменения схемы согласовать с потребителем, не выдумывать неподдерживаемые поля.
- `SHA256SUMS` перечисляет `l4setup.exe` и финальный `l4tools-release.json`, но **не самого себя**. Манифест не должен хешировать сам себя или образовывать цикл с `SHA256SUMS`. Хеш самого списка можно хранить в отдельном отчете приемки.
- Проверить содержимое пакета: без PIN/ключей/учетных данных, без GUI/elevation helpers, несовместимых service logon/recovery настроек, необходимости скачать неизвестный exe во время установки. Secure ACL/config сохраняются при распаковке.
- Сборка должна пройти вместе со всеми относящимися тестами измененных модулей. Для изменений Python-утилиты публикации — ее собственные проверки; несвязанные backend/frontend тесты не запускать, если их код не менялся.

### 2.3. Передача кандидата на 5A

Передать агенту 5: точный локальный путь, SHA-256 каждого артефакта, версии компонентов/OS, результаты сборок и тестов, инструкцию запуска setup с новыми режимами, известные ограничения. Хранить кандидат неизменным до решения приемки.

Испытания требуются **до** публикации. Не создавать успешную запись релиза в `releases.jsonl` на этапе локальной сборки.

## 3. Этап 4B — Публикация только принятого кандидата

Реестр: `https://l4tools-generic.ar.cloud.ru/l4tools/1.7.2/`. Для этой операции не нужен доступ к рабочим киоскам. Учетные данные `AR_GENERIC_KEY_ID` / `AR_GENERIC_KEY_SECRET` получать из окружения или некоммитируемой конфигурации; не читать/печатать сырой `.env`, не выводить Authorization.

1. Проверить отчет 5A: обязательные сценарии прошли, хеши совпадают с кандидатом, нет открытого дефекта UAC/session/recovery. Непроверенные обязательные OS не отмечать пройденными.
2. Проверить семантику Generic API и существующего publish-скрипта. `HEAD` и затем `PUT` сами по себе **не обеспечивают** иммутабельность при гонке. Использовать поддерживаемый create-only/conditional механизм; если его нет — один издатель и запрет перезаписи, явно зафиксировать ограничение.
3. Если версия уже существует, сравнить все опубликованные файлы: полностью совпадают — идемпотентная проверка без перезаписи; отличаются — остановка и согласование. `401`/`403`/timeout не означают «файла нет». Частичная публикация требует сверки каждого существующего файла, не удаления каталога.
4. Публиковать только разрешенный список артефактов, не wildcard со всем `dist`. Если потребитель использует release-manifest как признак готовности, загружать его последним. Многофайловый PUT не атомарен: набор считается доступным лишь после проверки всех файлов и сумм, не после первого `200 OK`.
5. После разрешения и проверки возможностей утилиты выполнить штатную команду:

```powershell
uv run python deploy\publish_l4tools.py --dist tools\dist --version 1.7.2
```

6. Выполнить HTTPS GET каждого опубликованного файла и локально вычислить SHA-256, сравнить с принятым кандидатом. `HEAD`/size/ETag не заменяют проверку байтов; `Digest` может отсутствовать или быть не hex, нельзя заранее требовать `digest: sha-256=<hex>`.
7. Записать успешный аудит `artifacts\l4tools\1.7.2.json` / `releases.jsonl` только после проверки полного набора. Повтор той же публикации не создает дублирующую успешную запись. При частичном сбое зафиксировать незавершенность, без маскировки под релиз.
8. Передать URL и результаты агенту 5 для 5B. Контрольная сумма — проверка целостности, не замена подписи/доверенного происхождения. Не отключать системные защиты ради запуска неподписанного пакета.

## 4. Definition of Done

1. **4A готов:** собран проверенный x86/x64 кандидат `1.7.2`, состав и метаданные фактические, хеши непротиворечивы; отчет передан на 5A.
2. **4B готов:** есть успешная 5A и разрешение на публикацию; опубликованы те же байты, повторное скачивание и аудит подтверждены.
3. Нет перезаписи существующей другой версии `1.7.2`, утечек секретов, автодеплоя на киоски или коммита бинарников. Никаких новых коммитов без отдельного поручения.
4. Если стенд, совместимость или разрешение недоступны — указать, что завершена только 4A и что блокирует 4B; не заявлять релиз готовым.
