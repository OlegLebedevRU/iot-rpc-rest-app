# Задание 5 (Шаг 6): Стендовая приемка tools v1.7.2 и проверка доставки

## 1. Роль, этапы и безопасность

Ты Windows QA-инженер. Обязателен [обзор шага 6](prompt_step6_stacks_overview.md). Требуется доказать предсказуемую работу киоска, а не только успешный запуск exe или наличие лог-строки.

- **5A:** испытать локальный кандидат после 4A; это обязательный барьер **до публикации**.
- **5B:** после 4B проверить, что по публичным URL доставляются те же испытанные байты.
- Использовать выделенную Windows-машину/VM со snapshot/backup и локальной либо out-of-band консолью восстановления. Не выполнять lock/logoff/reboot/power-loss, kill или тесты активного платежа на рабочем терминале.
- Согласовать конкретный стенд/SN, OS, разрядность и допустимые действия; не использовать терминал 70 или любой другой production SN по умолчанию. Действия ниже — сценарии приемки, не разрешение немедленно выполнить их на текущем ПК.
- Проверки требуют подготовленных профилей: standard user, split-token administrator, уже elevated administrator; Explorer shell и целевой kiosk/custom-shell. Не отключать UAC ради теста.
- Основной стенд Windows 10 x64; дополнительно проверить заявленные релизом Windows 7/POSReady 7/11 и x86/x64 по реальному составу payload. Отсутствующую платформу отметить `NOT RUN`, а не считать проверенной через WOW64.
- Если для реализации понадобятся исправления, передать их владельцу и повторить затронутую матрицу на новом кандидате. Не подменять результаты теста предположениями.

## 2. Подготовка evidence

Получить от агентов 1, 2A, 2B, 3, 4: SHA-256 кандидата, версии, CLI modes/exit codes, локальные probes и ожидаемые ответы, startup/stop/recovery limits, политику опасных действий. Для задания 2 нужны отдельно результат [2A (app1)](prompt_step6_agent_iot_rpc_rest_app_quick_actions.md) с REST/WS-схемами, ACK/NACK, бюджетами и совместимостью, затем результат [2B (MenuBuilder)](prompt_step6_agent_menubuilder_quick_actions.md) с UI/BFF и интеграционными проверками. Зафиксировать ревизии обеих частей и consumer; результат одной части не заменяет другую.

Зафиксировать baseline: OS/build/архитектура, UAC и тип shell, SID/сессия/IL без секретов, службы (состояние, startup type, зависимости и recovery), версии/хеши файлов, состояние сертификата и конфигурации, доступность локального/внешнего канала. Отпечаток сертификата можно использовать для сравнения; приватный ключ/PIN не экспортировать.

Примеры read-only проверок в разрешенной консоли стенда:

```powershell
Get-Service -Name Leo4Proxy,mosquitto,L4Con,L4Superv
Get-FileHash -Algorithm SHA256 -LiteralPath .\tools\dist\l4setup.exe
whoami /user
whoami /groups
```

Точные локальные status endpoints брать из handoff агента 3, не предполагать, что одна строка `ready` на HTTP-порту доказывает готовность всех служб. Фиксировать время начала/окончания и process exit code; для GUI-exe использовать runner, который действительно ждет завершения, не старое значение `$LASTEXITCODE`.

## 3. Этап 5A — Матрица обязательной приемки

Для каждой строки: `PASS / FAIL / NOT RUN`, фактическое поведение, версия/хеш, измерения и ссылка на evidence. Любой `FAIL` безопасности/восстановления блокирует публикацию. `NOT RUN` обязательной проверки также не дает разрешения на выпуск.

### 3.1. Setup: человек контролирует, процесс выполняется сам

| Сценарий | Ожидаемый результат |
|---|---|
| `--help`, `--version` без прав | Работают без UAC, файловых изменений и GUI |
| Не elevated: без флагов, `--silent`, `--interactive` | Exit `20`, нет consent/credential/PIN окон и изменений; интерактивность не дает права self-elevation |
| Конфликт `--silent --interactive`, неверные аргументы | Конечная ошибка без GUI/изменений |
| Elevated unattended / Session 0 | Ни одного окна, английский лог/summary; отсутствующий PIN/сессия не оставляет процесс ждать человека |
| Elevated `--interactive` на выделенной консоли | До Install видны план/версия/перерыв/лог; после подтверждения полный исправный проход без дополнительных кликов |
| Медленный progressing START_PENDING >30 с | UI отзывчив, elapsed растет, автоматически продолжает ожидание до 120 с; Retry не требуется на 30-й секунде |
| Stall, STOPPED с ошибкой, предел 120 с | Понятная причина; нет вечного ожидания; unattended — ненулевой код, interactive — Retry/Details/Cancel |
| Retry при уже RUNNING или START_PENDING | Перечитывает состояние; нет лишнего restart/повторного StartService |
| Cancel / закрытие окна на разных фазах | Безопасная граница/восстановление, честный cancelled/failed; не смешанные файлы и не exit 0 |
| Нет сертификата, неправильный PIN, Skip activation | Английский UI, секрет не в логе; skip = activation_required, не ready; unattended без PIN-диалога |
| Обрыв ответа активации после запроса | Сверка фактического результата; нет слепого повторного выпуска сертификата/расхода PIN |
| Не-ASCII путь/имя пользователя | Unicode-пути корректны, нет поврежденного текста или ошибочного поиска файлов |

Измерить отдельные бюджеты: до 120 с на службу, до 480 с на полный старт четырех служб, до 60 с на проход probes. Проверить также stop-timeout 120 с на службу, отсутствие busy loop и отсутствие popup из дочерних утилит. Не вводить критерий «вся установка ≤2 с».

### 3.2. Идемпотентность и обновление

| Сценарий | Ожидаемый результат |
|---|---|
| Повтор `1.7.2`, все исправно | Только проверки, exit 0; бинарники/config/сертификат не переписаны, PID/start times служб не изменились |
| Та же версия, служба остановлена/локально нездорова | Безопасная диагностика/старт, не пропуск по строке версии и не полная переустановка |
| `--repair`, поврежденный бинарник | Восстановлен управляемый файл; настройки, SN, ключ и сертификат сохранены |
| Установлена версия новее | `downgrade_blocked`, в том числе с `--repair`, до stop/изменений |
| Отсутствует/поврежден state, второй setup | Reconcile с реальностью / setup_busy; без сброса настроек и гонки замен |
| Мало места, битый payload, неподходящая OS/архитектура | Отказ в Prepare до остановки рабочего комплекта |
| Файл занят / служба не останавливается | Конечный отказ/восстановление, без reboot/deferred replacement/kill чужих процессов |
| Upgrade со старой версии | Payload готов до stop; обратный останов, сохранение config/cert, новая версия проверена до фиксации installed_version |
| Ошибка копирования/локального старта | Проверенный ограниченный rollback; отчет различает failed новой установки и восстановление старого набора |
| Crash установщика / отключение питания VM на границе замены | После разрешенного restart нет запуска смешанного комплекта; boot-recovery без UAC/входа человека либо явный запрет unattended upgrade до реализации такой гарантии |
| Запуск upgrade через L4Con, затем stop L4Con/потеря сети | Независимый setup не погибает с каналом/Job Object; итог доступен локально и после reconnect, повтор не дублирует установку |
| Сеть пропала при исправных новых локальных службах | Новый набор сохраняется, degraded/nonzero; нет rollback/перевыпуска сертификата из-за сети |

В тесте владения запустить отдельный безвредный процесс с совпадающим именем: он не должен быть завершен drainage. Сравнить config и thumbprint до/после. Отдельно проверить, что платежное приложение не закрывается и не перезапускается установщиком.

### 3.3. Права, ввод, курсор и ограничения Windows

| Сценарий | Ожидаемый результат |
|---|---|
| Split-token admin и требование High IL | Проверенный полный токен того же SID/session; l4desk High IL, нет UAC |
| Уже Full token | Агент не понижен из-за выбора связанного limited token |
| Standard user без linked token при требовании High IL | Явный insufficient_integrity, без SYSTEM fallback/повышения учетной записи и без ложного input-ready |
| Standard user и проверенный Medium IL профиль киоска | Ввод работает без ненужного повышения, права пользователя не меняются |
| Default token / ошибки доступа / смена сессии | Проверка фактических прав и конечный безопасный отказ; не произвольная RDP-сессия |
| Нет пользователя / lock / disconnected | Службы остаются живы; input запрещен, нет autologon/unlock/Winlogon automation |
| Нормальное и elevated окно на default desktop | Левый/правый клики реально обрабатываются; виден системный курсор; координаты совпадают с видео |
| Mouse/key down → up | Фактический порядок и пауза около 40 мс с учетом планировщика, без залипания при ошибке/потере lease |
| Потеря lease/epoch/TTL, дубль command_id, reconnect | Нет нового/повторного ввода по старой команде; ACK не приписан новой сессии |
| Alt+F4 / Win+D в штатном профиле | NACK action_blocked_policy; нельзя обойти обычными key_event/модификаторами |
| F12 вне проверенного профиля | Отказ; не обещать открытие диагностики в любом приложении |
| Обслуживание явно разрешено, тестовая безопасная цель | Подтверждение только в браузере оператора; разрешенный ввод; основной киоск/shell/неизвестная цель все равно запрещены |
| Progman/WorkerW/taskbar/custom shell/смена фокуса | Безопасный отказ; guard не считается доказательством безопасности любого другого окна |
| Искусственно вызванный secure desktop на стенде | Агент не вводит/не снимает видео с него; показывает недоступность, не stale-frame «все работает» |
| UI: панель, полосы видео, contextmenu | Нет случайного клика по киоску; один правый клик — одна команда |
| ACK injected / partial failure / timeout | Только подтвержденная передача ввода, не обещание эффекта; без автоматического retry |

Тест secure desktop выполняется намеренно QA через локальную консоль **вне** тестируемого автономного workflow. Отсутствие UAC проверяется наблюдением рабочего/защищенного desktop и журналом/доступным trace всего сценария, а не одним снимком списка `consent.exe`. Моки WinAPI и строка `Sleep(40)` в логе не заменяют реальный тест ввода.

### 3.4. После закрытия setup: киоск без администратора

- Закрыть setup; проверить независимость служб от GUI и сеанса установщика. В отдельном тесте завершить обслуживающую сессию: службы не исчезают; агент обслуживает только разрешенную сессию киоска.
- Выполнить **разрешенную QA перезагрузку стенда**: четыре службы стартуют по SCM без ручного логина администратора и UAC. Без kiosk-user session remote input явно недоступен. Если образ предполагает autologon, проверять уже подготовленный образ, не настраивать его тестовым скриптом.
- Отключить/вернуть сеть: локальные службы продолжают работать, reconnect без restart всего комплекта, без окон и replay команд.
- Имитировать отдельный crash службы/l4desk/FFmpeg: восстанавливает только назначенный владелец, с конечными лимитами и задержками. Нет restart storm или автоматической перезагрузки Windows.
- Ошибка загрузки помощника/crash не показывает critical-error, WER или консольное окно на киоске; диагноз остается в логе. Проверять реальные процессы, не только наличие error-mode флага в исходнике.
- Штатный stop/lease expiry не вызывает recovery как после crash. Lock/unlock и смена сессии не переносят старый ввод/поток в новую эпоху.
- Проверить ACL: непривилегированный пользователь не подменяет exe/config высокопривилегированного агента, service ImagePath или управляющий IPC. Не выводить защищенные секреты для доказательства доступа.
- Наблюдать штатную работу не менее **30 минут**, включая сетевой сбой и recovery; фиксировать рестарты, окна, CPU/RAM и рост лога. Это минимальный smoke-интервал, не доказательство длительной безотказности.

## 4. Этап 5B — Проверка опубликованных байтов

После успешной 5A и публикации агентом 4:
1. Скачать по HTTPS `l4setup.exe`, `l4tools-release.json`, `SHA256SUMS` из `https://l4tools-generic.ar.cloud.ru/l4tools/1.7.2/` в отдельный каталог стендовых артефактов.
2. Локально вычислить SHA-256 каждого файла и сверить с неизменным кандидатом 5A. `HEAD 200`, размер, ETag или непроверенный формат Digest недостаточны.
3. Проверить версию и манифест скачанного установщика безопасным `--version`; не запускать установку на текущем ПК по факту скачивания.
4. Любое несовпадение — выпуск не подтвержден; не перезаписывать реестр и не изменять ожидаемый хеш под полученный файл.
