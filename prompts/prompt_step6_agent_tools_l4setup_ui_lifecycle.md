# Задание 3 (Шаг 6): l4setup — Понятная установка до готовности и безопасное обновление

## 1. Роль и границы

Ты Windows / C Systems Developer. Реализуй один простой установочный процесс для standalone-киоска: человек понимает происходящее и один раз подтверждает изменения, затем исправный сценарий автоматически доходит до запущенных и проверенных служб.

Обязателен [обзор шага 6](prompt_step6_stacks_overview.md), особенно режимы запуска и контракт готовности. Не создавать универсальный транзакционный framework, новый постоянно работающий updater или дополнительный watchdog.

Точки входа в `tools\l4setup`: `src\main.c`, `cert_phase.c`, `services.c/.h`, `drainage.c`, `uac.c`, существующая распаковка и состояние, `res\l4setup.rc`, `resource.h`, манифест. Сначала проверить реальную структуру; названия здесь — ориентиры, не повод создавать дубли модулей. Версию `1.7.2` синхронизирует агент 4.

## 2. Явные режимы и права до изменений

- `--interactive` — GUI только для присутствующего обслуживающего человека; без него unattended. `--silent` явно запрещает окна; конфликт режимов — ошибка без GUI. Все обертки/скрипты должны передавать выбранный режим, не угадывать его по desktop или родительскому процессу.
- Манифест `asInvoker`, `uiAccess="false"`. Ни на одной ветке не вызывать self-elevation / `ShellExecuteExW("runas")`, `highestAvailable` или скрытую задачу повышения прав. Человек при первичной подготовке запускает повышенный процесс самостоятельно.
- Не elevated → exit `20` и `Administrator privileges are required. No changes were made.` в доступный stderr/лог. Это **код продукта**, Win32 access denied равен `5`. Проверка до PIN, сети, записи файлов и регистрации служб; отсутствие прав на лог не должно порождать окно или скрывать исходный код.
- `--help`/`--version` — без прав, диалогов и побочных действий. Невозможный интерактивный запуск (Session 0, нет доступного desktop) завершается, а не ждет невидимого окна.
- Все дочерние утилиты запускаются без окон, с конечными таймаутами, контролируемыми аргументами и возвратом результата. Никаких credential prompts, интерактивного PowerShell или открытия браузера на терминале.

## 3. Спокойный UI: одна операция, одно окно

### 3.1. До старта

Показать в одном окне:
- обнаруженную и целевую версии, `Install / Upgrade / Repair / Verify`;
- четыре службы и что будет изменено/сохранено;
- состояние сертификата, необходимости активации и прав;
- ожидаемый перерыв связи при обновлении, отсутствие автоматического reboot/logoff;
- путь установки и лога, кнопку запуска и `Cancel`.

Проверить единственный экземпляр установки, OS/архитектуру, свободное место с запасом под staging+backup, защищенность путей/ACL, доступ к SCM/ключу, совместимость профиля сессии/IL, pending reboot и готовность payload. При обновлении работающего платежного киоска использовать существующий признак допуска к обслуживанию; если его нет — явное подтверждение отсутствия активной операции до stop, без автоматического закрытия платежного приложения. Для unattended такой допуск должен быть предоставлен доверенным инициатором заранее.

Не менять учетные записи, autologon, shell, блокировку, Windows Update или UAC. Не лечить несовместимый образ киоска случайными registry tweaks. Нужна перезагрузка/другой профиль — сообщить причину до остановки и не выполнять ее автоматически.

### 3.2. Во время и после

- Один GUI, один worker, Win32 message loop; обновления через сообщения. Фазы `Check → Prepare → Stop → Update → Start → Verify → Finish`. Не блокировать UI `Sleep`/сетевыми вызовами, не поднимать MessageBox на каждую службу.
- Таблица четырех служб: `Pending / Starting / Running / Checking / Ready / Failed`, elapsed time, текст текущей операции. Не показывать фиктивный процент и «зависание» без объяснения.
- Исправный путь после подтверждения выполняется без дополнительных кнопок. Никаких автозакрытий, countdown и требований нажать Retry за ограниченное время. Финал остается до `Finish`.
- Кнопки при проблеме: `Retry`, `View details`, `Cancel`. Retry повторяет только безопасную фазу, не весь setup; нет `Continue` с пропуском обязательной службы.
- `Cancel` и закрытие окна означают запрос на отмену на ближайшей безопасной границе. Во время замены/восстановления показать `Finishing the current operation safely...`; не убивать worker и не бросать смешанный набор файлов.
- Итог явно различает запущенные службы, активацию, внешнюю связь и remote input. При неготовности видны причина, что сохранено/восстановлено и конкретный следующий шаг. Секреты в details не выводятся.

### 3.3. PIN и язык

- Все собственные UI/логи setup — английские, Win32 API — Unicode; английский текст не заменяет правильную работу с не-ASCII путями.
- Заголовок `Leo4 Setup - Terminal Activation`; текст `Enter the 6-digit terminal PIN to issue a certificate:`; кнопки `Activate`, `Skip activation`, `Cancel`. `Skip` и `Cancel` имеют разные действия/идентификаторы.
- Валидировать ровно шесть цифр. Не включать PIN в логи, summary или аргументы процессов. При существующем пригодном сертификате повторное получение не запускается.
- `Skip activation` предупреждает, что терминал еще не готов, и приводит к `activation_required`, не к exit `0`. Запустить только компоненты, которым безопасно работать без сертификата; зависимые отметить `Blocked` с причиной.
- Unattended никогда не спрашивает PIN. При отсутствии сертификата использовать только уже утвержденный неинтерактивный канал активации; иначе закончить с явной неготовностью, не создавать новый способ передачи секрета.
- Timeout активации не доказывает, что сервер не выпустил сертификат. Перед Retry сверить фактическое состояние существующим протоколом; не повторять выпуск/расход PIN вслепую. Нельзя подтвердить результат — явная незавершенность без автоматического повторного запроса.

## 4. Старт служб: ждать автоматически, но не бесконечно

Проверить зависимости и закрепить порядок `Leo4Proxy → mosquitto → L4Con → L4Superv`. Задать автозапуск и зависимости SCM там, где это реальные зависимости служб; готовность сетевого канала не превращать в вечный `START_PENDING`.

1. Перед действием вызвать `QueryServiceStatusEx`. `RUNNING` → health check без restart; `START_PENDING` → ждать; `STOP_PENDING` → ограниченно дождаться завершения; `STOPPED` → один `StartService`. `ERROR_SERVICE_ALREADY_RUNNING` требует перечитать состояние, не считать аварией.
2. На 30 с показать `Taking longer than usual; still waiting...` и продолжать автоматически. Проверять `dwCheckPoint`, `dwWaitHint`, exit codes и абсолютный монотонный deadline **120 с на службу**; hint не продлевает его бесконечно. Опрос примерно раз в 0.5–2 с, без busy loop.
3. Немедленный `STOPPED` с ошибкой — показать причину, не ждать оставшиеся две минуты. Нет прогресса — диагностировать stall с учетом wait hint; дать безопасный Retry после завершения текущей попытки. В unattended не начинать бесконечные попытки.
4. Полный проход четырех служб ≤ **480 с**, итоговые probes локальной/внешней работоспособности ≤ **60 с на проход**. На экране/в логе раздельно видны SCM-ожидание и health/network check.
5. При таймауте интерактивный Retry перечитывает состояние и запускает новый ограниченный проход только для незавершенной части. Никогда не Stop/Start исправной службы для «повторной проверки».
6. Выбрать минимальные существующие проверки: `Leo4Proxy` — локальный health/status и сертификат; mosquitto — подключение по штатному локальному протоколу, не один TCP open; L4Con — штатный статус/готовность; L4Superv — локальный status плюс результат запуска агента для доступной сессии. Уточнить фактические endpoints и ожидаемые поля до реализации, не добавлять отдельный мониторинговый сервис.
7. Внешняя связь проверяется существующим безопасным ping/status, не платежом и не публикацией нового presence. Недоступность сервера/DNS при исправных локальных службах — `degraded`; не переустанавливать их и не перевыпускать сертификат.

## 5. Идемпотентность и upgrade без сюрпризов

### 5.1. Решение до остановки

- Мьютекс/существующая блокировка на весь install: второй экземпляр возвращает `setup_busy` без побочных действий. Не удалять чужую блокировку по таймауту.
- Версию сравнивать численно по компонентам, не лексикографически. `installed_version` — подсказка, не единственный источник истины: сверить манифест/хеши фактических бинарников, защищенную конфигурацию, регистрацию SCM, сертификат и health.
- Та же версия, все исправно → только verify, без переписи бинарников/конфигурации/сертификата и без рестартов. Обновить отчет допустимо. Не требовать ≤2 с ценой пропуска проверок; длительность измерить на стенде.
- Та же версия, служба остановлена/нездорова → сначала безопасный старт/диагностика; поврежденные файлы → repair. Отсутствующий/поврежденный `state.json` не повод стереть конфигурацию.
- Установленная версия новее пакета → отказ `downgrade_blocked`, включая `--repair`. Устаревшая → upgrade. `--repair` восстанавливает управляемые файлы, но не сбрасывает identity, конфигурацию и ключи.

### 5.2. Подготовка, останов, замена

1. **До остановки:** полностью подготовить payload в защищенном staging на том же томе, проверить хеши, архитектуру, свободное место, сохранность конфигурации. Не качать зависимости после обрыва собственного канала управления. SHA-256 проверяет целостность, не происхождение пакета — использовать доверенный канал доставки.
2. Сохранить предыдущие заменяемые файлы и настройки SCM/конфигурации. Не экспортировать приватный ключ сертификата. Зафиксировать простой маркер незавершенной установки с фазой и old/target version в существующем состоянии; не создавать сложный журнал транзакций.
3. Перед stop остановить прием новых задач и согласовать ограниченный drainage с существующими владельцами. Установщик, запущенный через L4Con, должен быть заранее передан независимому процессу с защищенным локальным отчетом и не погибать при остановке родительской службы/Job Object. Проверить это на стенде; без такого пути unattended upgrade не разрешать.
4. Остановить в обратном порядке. На 30 с показывать задержку, конечный предел — **120 с на службу** с проверкой SCM; после исчерпания не продолжать замену занятых файлов. При отмене до замены вернуть ранее работавшие службы.
5. l4superv не должен возрождать l4desk во время stop. Не завершать платежное приложение. Запрещены `taskkill /IM`, kill по одному имени/PID и «убить все ffmpeg». Для принадлежащих комплекту зависших дочерних процессов допустимо конечное завершение только после graceful stop и подтверждения владения через сохраненный handle/путь/сессию/время создания. Если владение не доказано — отказ, не риск потери чужого процесса.
6. Дождаться освобождения файлов. Не использовать reboot, `MoveFileEx(...DELAY_UNTIL_REBOOT)` или deferred replacement. Не перезаписывать заблокированный файл и не выдавать частичную замену за атомарную установку.
7. Заменять только управляемые файлы при остановленных потребителях. Набор файлов не является одной атомарной операцией: использовать staging+backup и проверяемое восстановление. Сохранять пользовательские настройки; необходимые изменения конфигурации — минимальный merge с backup, без сброса всего файла.
8. Восстановить корректную регистрацию SCM/ACL, запустить и проверить локальные компоненты. Только затем атомарно записать `installed_version` через временный файл и replace. Не затирать неизвестные поля состояния.

### 5.3. Неуспех, прерывание, восстановление

- Ошибка замены/локального запуска → один ограниченный rollback предыдущих файлов и настроек, запуск прежнего набора, проверка. Если восстановлено, сообщить `failed` с `rollback=restored`, не `ready` новой версии. Если не удалось — конкретная причина, без loop/reboot/dialog в unattended.
- После срыва сети, но при исправной локальной версии, rollback не нужен: сохранить новый установленный набор и результат `degraded`.
- После process crash/потери питания следующий запуск читает маркер и сверяет реальные файлы; не доверяет только `installed_version`. Для самостоятельного старта после питания описать и проверить минимальный существующий boot-recovery путь **до** изменения live-файлов: восстановление предыдущего проверенного набора до запуска зависимых служб, без нового updater-сервиса, UAC и авторизации пользователя. Нет такого пути — unattended обновление не допускать, ограничиться явно обслуживаемым режимом и честно отметить ограничение.
- Backup не удалять до успешной локальной проверки. Cleanup касается только staging/backup текущей операции; не удалять чужие файлы или ключи. Нет автоматического downgrade/reinstall на каждом boot.

## 6. Результат и runtime

- `install_summary.json` и exit codes — по обзору. Перед реализацией зафиксировать совместимую с текущим CLI таблицу ненулевых кодов для incomplete/cancel/failure/busy/downgrade и передать агенту 5. Exit `0` только `ready`; exit `20` только отказ по правам.
- В `ready` четыре службы прошли локальные probes, активация и канал управления подтверждены. Отдельно сообщить remote input: при отсутствии входа он недоступен, хотя службы могут быть готовы. Несовместимый IL при активной целевой сессии не скрывать статусом «все работает».
- После закрытия setup службы стартуют через SCM независимо от GUI/сеанса установщика. Проверить startup type, зависимости и конечную recovery-политику. Ни reboot recovery action, ни GUI запуска, ни интерактивная service logon не допускаются.
- Не конкурировать с l4superv за его дочерние процессы. Сеть восстанавливается штатным reconnect без перезапуска всего комплекта и без replay пользовательских команд.

## 7. Проверки и Definition of Done

1. До исправления воспроизвести UAC/timeout/повторную установку соответствующими тестами. Покрыть режимы, коды возврата, PIN skip/cancel, UI cancel/close, no-session и non-ASCII пути.
2. Проверить SCM-сценарии: уже RUNNING, медленный progressing START_PENDING (дольше 30 с), stalled/pending за пределом 120 с, STOPPED с ошибкой, Retry без лишнего restart; все ожидания конечны, UI отзывчив.
3. Проверить same-version healthy/unhealthy, numeric version, newer-version отказ, `--repair`, concurrent setup, битый state, нехватку места, locked file, rollback, crash/power-loss recovery и сохранение сертификата/конфигурации.
4. Выполнить штатную x86/x64 `/MT` сборку l4setup и релевантные native-тесты. Проверить упакованный манифест и вспомогательные исполняемые файлы, а не только исходный `.manifest`.
5. Пройти [стендовую матрицу](prompt_step6_agent_stand_verification.md), включая обслуживание через останавливаемый L4Con, запуск после закрытия setup/выхода обслуживающего пользователя и восстановление связи. Не выполнять разрушительные проверки на платежном терминале.
6. Передать агентам 4/5 фактические probes, CLI modes/коды, timeout/recovery limits, критерии `ready`, список изменяемых файлов и подтвержденные ограничения. Недоступный boot recovery нельзя объявлять реализованным.
