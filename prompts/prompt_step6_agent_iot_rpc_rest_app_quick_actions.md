## 2. Команды и доверенная серверная граница

- Сохранить действующие REST/WS endpoints и envelopes; расширить их, не создавать параллельную шину. Входные действия UI описаны в 2B, MQTT envelope — в разделе 4 обзора.
- `mouse_click`: `button` только `left` / `right`, при отсутствии `left`; `middle` и неизвестные значения отклонять. `x`, `y` — целые `0..65535`; не округлять и не обрезать невалидные координаты молча.
- `shortcut_action`: `action` только `f12` / `alt_f4` / `win_d`. Неизвестные значения — отказ, а не fallback в произвольные клавиши.
- UI передает только действие, параметры и `client_ref`. Не доверять переданным браузером owner, SN, scope, `command_id`, lease или эпохе. BFF аутентифицирует пользователя и формирует доверенный контекст; app1 проверяет подлинность внутреннего вызова штатным механизмом и привязку этого контекста к устройству/lease. Не считать произвольные заголовки доказательством прав.
- Одинаково для REST и WS проверять owner/tenant, актуальную lease со scope `input`, активный **desktop** stream, SN, source/epoch, TTL и доступную серверу политику. Camera/view-only, чужая или устаревшая lease не дают ввод. Сохранить проверки consumer; сервер не отменяет локальные guards терминала.
- `Alt+F4` / `Win+D` по умолчанию запрещены на рабочем киоске; разрешение только для подтвержденного профиля обслуживания. `F12` — только для проверенного профиля приложения. Браузерное подтверждение не меняет терминальную политику. Нельзя обойти ограничения прямым WS, REST или обычным `key_event`.
- Новые действия разрешать только при подтвержденной совместимости consumer по существующим version/capability сведениям. Неизвестная/старая версия — явная недоступность с причиной; не заявлять поддержку по одной версии app1.
- app1 формирует доверенный envelope из обзора в `srv/{SN}/ctl`. Команды и ACK/NACK — **без retain**; QoS 1 допускает дубликаты, dedup по `command_id` сохраняется на существующих границах, включая consumer. `client_ref` не заменяет `command_id`.
- Нет автоматического retry ввода при timeout/reconnect, выдачи нового `command_id` для скрытого повтора или очереди действий для следующей сессии. Потерянный ACK означает неизвестный результат, а не разрешение повторить клик.

## 3. ACK/NACK и корреляция

- Сохранить существующий envelope ответа и соответствие `command_id ↔ client_ref`, lease/epoch. Принимать результат только для соответствующей команды и сессии; поздний ответ прежней эпохи не должен завершать новую команду.
- HTTP-принятие запроса или MQTT PUBACK не означает исполнение ввода. `injected` передается только как результат consumer и означает принятие событий Windows, **не** закрытие окна или открытие меню.
- Согласовать с агентом 1 и передать без потери причин: `action_blocked_policy`, `action_blocked_winlogon_guard`, `desktop_locked`, `session_unavailable`, `insufficient_integrity`, `input_injection_failed`. Сопоставить их с реальными схемами REST и WS, не менять envelope несогласованно.
- Timeout/частичное выполнение не превращать в success. Сохранить неизвестный результат для UI без повтора; локальный отказ в валидации не выдавать за терминальный ACK/NACK.
- Не добавлять команды обхода UAC, разблокировки или входа в Windows. Не логировать JWT, PIN, ключи, полный чувствительный payload или содержимое клавиатурного ввода.

## 5. Проверки и Definition of Done

1. Для исправляемых ошибок сначала воспроизведение с failing test. Новые контрактные тесты: левый default, правый клик, допустимые action при разрешенной политике, unknown/middle, нецелые/внедиапазонные координаты, неподтвержденная/старая версия consumer.
2. REST и WS проверить отдельно: неверные owner/tenant/lease/scope/SN/source/epoch, истекший TTL, camera/view-only, обход policy через `key_event`, неавторизованный внутренний вызов. Отказ не публикует команду ввода.
3. Проверить envelope, отсутствие retain, `command_id ↔ client_ref`, dedup, новые ACK/NACK, поздний ответ, потерю ACK и reconnect без retry/replay; HTTP/PUBACK не дает ложный `injected`. Проверить бюджеты stream-start/inventory и сохранение ошибок.
4. Выполнить штатные тесты app1 и все релевантные downstream/интеграционные проверки, не ограничиваться одним файлом. Для Python использовать `uv run pytest`, `uv run ruff check --fix <src_dir>`, `uv run ruff format <src_dir>`, `uv run pyright <src_dir>` по реальной структуре и правилам репозитория. Не использовать production secrets. Проверки внешнего consumer подтверждать evidence агента 1; недоступные проверки явно отметить, не заменять mock-сервисом.

Передать агентам **2B и 5** короткий результат: ревизию app1 и consumer, реальные REST/WS-схемы запросов/ответов с безопасными fixtures, источник доверенных полей, ACK/NACK и корреляцию, версии/признаки совместимости, бюджеты и ошибки, выполненные тесты и ограничения.
