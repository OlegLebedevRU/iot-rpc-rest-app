# Обязательный стандарт выполнения промптов L4Desk

Версия стандарта: `1.2.0`

Этот документ является обязательной частью каждого промпта из данного каталога. Если локальное тело промпта расходится с этим стандартом, действует более строгое правило. Архитектурный источник требований: `..\l4desk-architecture.md`. Единственный источник межагентной передачи фактически принятых контрактов: `contract-handoff.md`.

## 1. Непереговорные правила

1. Один запуск работает ровно с одним `scope_project`, указанным в промпте.
2. Запрещено просматривать исходный код, менять файлы, запускать команды, тесты, commit, push или deploy в любом другом проекте/стеке.
3. Разрешено читать текущее тело промпта, этот стандарт и `contract-handoff.md`; архитектуру — только в явно указанных разделах. Дополнительно разрешён конечный набор data-only артефактов принятого входа по явному read grant §10. Это не разрешение читать исходники или весь каталог provider.
4. Нельзя читать репозиторий provider/consumer-соседа для восстановления контракта. Нельзя использовать память, предыдущий чат, предположение, deployed API или похожую реализацию вместо входного handoff.
5. Межпроектный контракт существует для агента только тогда, когда в `contract-handoff.md` имеется ровно один завершённый блок требуемого `handoff_id` со статусом `ACCEPTED`, адресованный текущему `prompt_id`.
6. Если обязательный handoff отсутствует, неоднозначен, имеет `DRAFT/REJECTED/BLOCKED`, содержит `TBD/TODO`, не имеет digest/версии/ссылок на артефакты либо не адресован текущему prompt, агент обязан немедленно завершить работу со статусом `BLOCKED_CONTRACT`. Адресация определяется `consumers` или отдельным адресным допуском контроллера по §8; остальные проверки обязательны в обоих случаях. Код и инфраструктура при блокировке не меняются.
7. Контракт не дополняется «очевидными» полями. Любая недостающая семантика, идентификатор, enum, error code, схема, пример или правило совместимости — blocker и запрос corrective/provider prompt.
8. Не менять и не включать в commit посторонние пользовательские изменения. Запрещены destructive git-команды и скрытое расширение scope.
9. Секреты, production credentials, токены, ключи и содержимое `.env` не фиксируются в коде, отчёте или handoff.
10. Новый MQTT-клиент или изменение MQTT-клиента запрещено начинать без явного значения `mqtt_client_type = main_app | extra_service` в принятом handoff. При отсутствии значения вернуть `BLOCKED_CONTRACT`. Presence-сценарий должен соответствовать проектным guidelines.

## 2. Contract gate — обязательное первое действие

До анализа кода и любых implementation/deploy команд выполнить gate. Для самого gate разрешены только чтение разрешённых документов, read-only проверка Git текущего scope, получение разрешённых immutable artifacts и вычисление digest (из текущего scope, без команд в соседнем проекте):

1. Открыть `contract-handoff.md`.
2. Найти каждый `required_handoff_id` по точным маркерам `HANDOFF:<id>:BEGIN/END`.
3. Убедиться, что блок встречается ровно один раз, `status: ACCEPTED`, `consumers` содержит текущий `prompt_id` либо `ALL_FOLLOWING` или имеется точный адресный допуск по §8, а `producer_prompt_id` уже завершён.
4. Сверить `contract_version`, `artifact_paths`, `artifact_sha256`, `compatibility`, `deployment_status` и `supersedes`; точная дополнительная привязка исторических Git-байтов допустима только по §10.4.
5. Выписать в рабочий отчёт точные входные версии и digest. Использовать только эти версии.
6. Проверить, что handoff непосредственно предыдущего шага каскада принят; это sequence gate даже тогда, когда его предметный контракт текущему шагу не нужен. Поле `consumers` выходного handoff должно перечислять все будущие prompt, указанные как потребители в реестре зависимостей, либо иметь точное значение `ALL_FOLLOWING`; только непосредственного `next_prompt_id` недостаточно, если artifact потребуется позднее.

Для первого шага `L4D-00A-TOOLS` входных handoff нет. Он всё равно обязан убедиться, что журнал находится в состоянии `READY_FOR_00A` и в нём отсутствует уже принятая конфликтующая запись его output.

## 3. Исследование только текущего проекта

1. Прочитать локальные `AGENTS.md`, `GUIDELINES.md`, README и runbook текущего проекта.
2. Зафиксировать baseline: branch/commit, версии, тесты, конфигурационные feature flags и состояние deploy.
3. Искать и открывать только файлы текущего `scope_project`.
4. При обнаружении межпроектной зависимости остановить соответствующую часть, записать blocker и предложить следующий изолированный prompt; соседний проект не открывать.
5. Выбрать минимальное additive решение без параллельной реализации console/video и без необоснованного нового сервиса.

## 4. Разработка и тестовая стратегия

1. До исправления бага создать воспроизводящий тест и подтвердить его падение.
2. Для новой функции сначала добавить тесты core logic, negative cases, идемпотентности, повторной доставки, гонок и граничных дат/timeout, применимые к scope.
3. Provider проверяет опубликованную schema/fixtures provider contract tests; consumer — consumer contract tests. Межпроектные тесты заменяются тестами против immutable artifacts из handoff.
4. Сохранить backward compatibility всех объявленных версий. Изменения API/schema выполняются additive и под feature flag, если это требуется контрактом.
5. Для денег использовать целые копейки, double-entry invariant, append-only corrections и отдельный учёт discarded kopecks; `float` запрещён.
6. Выполнить полный набор локальных lint/type/build/test команд текущего проекта и все downstream-тесты внутри этого же scope.
7. Не ослаблять, не удалять и не пропускать падающие тесты. При любом непройденном обязательном check итоговый статус — `BLOCKED_TESTS`.

## 5. Commit, push и deploy

1. Commit и push обязательны для implementation/release prompt и выполняются только после зелёных проверок. Baseline/docs prompt коммитит только созданный локальный отчёт/документацию, если это разрешено телом шага.
2. Использовать отдельную ветку `l4desk/<prompt-id-lowercase>`, если оператор не передал другую ветку. Не переписывать историю.
3. В commit включать только файлы текущего scope. Соблюдать локальные правила авторства/трейлеров.
4. Push выполняется только в remote текущего проекта. Зафиксировать branch и commit SHA.
5. Deploy выполняется только по локальному runbook и только текущего проекта. Для компонентов репозитория `etranprocessing` production host — только `user1@87.242.100.34` с утверждённым ключом и `ssh -n`; иной host запрещён без прямого указания владельца.
6. Перед использованием MCP Ops выполнить readiness-проверку RAM, disk и load и записать `READY` либо `DEGRADED/UNAVAILABLE`; недоступность MCP не блокирует штатный SSH deploy.
7. State-changing операции требуют предусмотренного подтверждения. Миграции выполняются только владельцем Alembic и только в назначенном prompt.
8. После deploy выполнить project-local smoke/contract probes, проверить rollback readiness и версии реально работающих артефактов.
9. Не объявлять `ACCEPTED`, если build/test/deploy/smoke неуспешен. Для docs-only шага deploy означает публикацию документа в его ветке/remote и проверку доступности commit.

## 6. Отчёт и передача контракта

Агент создаёт отчёт только внутри текущего проекта по пути, заданному локальным prompt. Отчёт содержит:

- scope и перечень реально изменённых файлов;
- входные handoff id/version/digest;
- решения и исключённый scope;
- результаты тестов с командами и итогами;
- branch, commit, push;
- migration/deploy/smoke evidence;
- rollback;
- риски и blockers;
- точный candidate-блок для единого `contract-handoff.md` либо ссылку на отдельный окончательный candidate по явно согласованному формату §9.

Runtime-агент не редактирует `contract-handoff.md`, потому что это нарушило бы правило одного проекта. Он формирует candidate-блок. Контроллер каскада проверяет отчёт и единственной append-only операцией добавляет блок в общий файл. Для `scope_project = l4desk-service` агент может добавить блок сам после проверки.

Следующий prompt запрещено запускать, пока candidate-блок не принят контроллером и не появился в `contract-handoff.md` со статусом `ACCEPTED`.

## 7. Допустимые финальные статусы

- `ACCEPTED` — все обязательные изменения, проверки, push, deploy/publish, smoke и candidate handoff завершены.
- `BLOCKED_CONTRACT` — входной контракт отсутствует или недостаточен.
- `BLOCKED_TESTS` — обязательная проверка не прошла.
- `BLOCKED_DEPLOY` — deploy/publish/smoke не завершён.
- `BLOCKED_SCOPE` — требуемое изменение относится к другому проекту.
- `REJECTED` — решение нарушает архитектурный инвариант или backward compatibility.

Любой статус кроме `ACCEPTED` останавливает каскад. Следующим разрешён только corrective prompt, зарегистрированный контроллером.

## 8. Адресная регистрация corrective prompt

Контроллер по явному подтверждению пользователя может добавить в конец `contract-handoff.md` отдельную запись `CORRECTIVE_REGISTRATION:<registration_id>:BEGIN/END`. Это разрешение на корректирующую работу, а не `HANDOFF`, provider-релиз, приёмка отчёта или подтверждение deploy. Старые handoff-блоки не редактируются и не отзываются ради добавления потребителя.

1. Промпт обязан указать `registration_id`. Между точными маркерами должна находиться ровно одна YAML-запись с `status: AUTHORIZED`, совпадающими `prompt_id`, `scope_project`, `scope_root`, `blocked_prompt_id`, `output_handoff_id`, `next_prompt_id` и путями отчёта/candidate. Контроллер фиксирует основание подтверждения пользователя и время UTC; runtime-агент не создаёт такие разрешения.
2. `authorized_inputs` задаёт конечный перечень `handoff_id`, `contract_version`, `producer_commit`. Набор идентификаторов должен точно совпадать с `required_handoff_ids` промпта; версии и коммиты — с исходными принятыми блоками. Допуск действует только для указанного `prompt_id` и scope, не наследуется исходным шагом, соседями или будущими FIX.
3. Только проверка адресации в `consumers` дополняется этой записью. Уникальность исходных блоков, `ACCEPTED`, версии, артефакты и их digest, полнота контракта, compatibility, deployment и проверка отзыва остаются обязательными. Допуск не разрешает чтение исходного кода соседнего проекта и не делает недоступные артефакты доступными.
4. `sequence_gate_handoff_id` указывает последний принятый основной шаг перед заблокированным. Для corrective проверяется он, а не ещё не принятый output заблокированного шага. Если этот ID отсутствует в `required_handoff_ids`, проверить только уникальность, ACCEPTED, отсутствие отзыва/несовместимой замены и producer completion по журналу — не его artifact_paths или consumers. Это sequence-only проверка, не повторная приёмка старого контракта. Предметные входы проходят полный gate. Регистрация сама не продвигает основной каскад.
5. Дубликат, несовпадение метаданных, недостающий input или запись `CORRECTIVE_REGISTRATION_REVOCATION:<registration_id>:BEGIN/END` со статусом `REVOKED` означают `BLOCKED_CONTRACT`. Исправление регистрации — новый ID после явного отзыва старого, без редактирования прежних байтов.
6. Разрешение не заменяет публикацию: перед запуском оператор публикует согласованные prompt, стандарт и журнал через commit/push по README. Агент фиксирует commit опубликованного пакета; при недоказанной публикации возвращает `BLOCKED_CONTRACT`.

Этот параграф и запись регистрации являются явным дополнением проверки адресации из §1 журнала; прочие требования журнала не меняются. Входные handoff ID не заменяются ID регистрации.

## 9. Отдельный candidate без самоссылки (`DETACHED_V1`)

Формат применяется только если запись регистрации содержит `candidate_format: DETACHED_V1`, `detached_candidate_approved: true` и точные `report_path`/`candidate_path`, совпадающие с промптом. Повторное согласование исполнителем не требуется. Для остальных шагов действует обычный формат.

1. Отчёт содержит результаты и путь к отдельному окончательному candidate, но не собственный digest и не конкурирующий окончательный candidate-блок. В нём указываются реальные коммиты реализации/проверенной runtime-версии; будущий commit самого отчёта не угадывается.
2. Зафиксировать окончательные байты отчёта, опубликовать его и evidence в commit R, проверить публикацию и вычислить SHA-256 отчёта по этим байтам. После этого отчёт не изменять; при изменении повторить фиксацию и расчёт.
3. Отдельный candidate содержит все канонические поля, точные HTML-маркеры, отчёт в `artifact_paths` с соответствующим lowercase SHA-256, `producer_report_path`, `report_commit: R` и `producer_commit` реализации. Артефакты привязываются к доступным immutable версиям; для файлов отчётного пакета используется R.
4. Опубликовать candidate отдельным commit C. Сам candidate не включается в собственные `artifact_paths` и не содержит собственного SHA-256 или C. В финальном ответе передать C, путь и вычисленный digest candidate; контроллер проверяет их независимо. Это разрывает обе самоссылки — по хешу файла и по хешу содержащего его коммита.
5. Контроллер сверяет отчёт именно из R, candidate из C, реализацию по `producer_commit` и фактически работающий артефакт. Проверка статуса отчёта, тестов, deploy/smoke, каждого digest и sequence gate не сокращается. Несовпадение отчёта с опубликованной версией или digest запрещает приёмку.
6. Только после независимой приёмки контроллер добавляет окончательный candidate в журнал. Публикация candidate исполнителем сама по себе не является принятием.

## 10. Самостоятельные контрактные артефакты и точные байты

1. Контроллер по явному поручению пользователя может выполнить отдельный документационный provider/corrective шаг в scope `l4desk-service`: экспортировать проверенный контракт текущего репозитория в data-only Markdown/JSON/YAML. Исходную реализацию контроллер читает только по конечному списку provenance-файлов; runtime-агент такого разрешения не получает. В отчёте указываются source commit, реальные проверки и ограничения, а не вымышленные runtime-тесты/deploy. Сначала публикуются документы и отчёт в commit A, затем handoff с digest каждого файла, включая отчёт. Для такого экспорта результат локальной проверки `VERIFIED` в отчёте достаточен только вместе с независимым подтверждением публикации A; `verification_status: VERIFIED` и окончательное ACCEPTED фиксируются контроллером в handoff после этого. Это узкое дополнение к правилам отчёта, не исключение для runtime-шага.
2. `external_artifact_reads` регистрации и промпта должны совпадать: `handoff_id`, `artifact_commit` и конечный список `paths`. Каждый файл должен входить в artifact_paths указанного принятого handoff и иметь SHA-256, immutable URL/commit. Разрешены чтение и digest этих bytes, в том числе скачивание по указанным URL из текущего scope. Запрещены wildcard, исполняемые исходники, import/exec артефактов, соседние git-команды и чтение дополнительных файлов по ссылкам внутри документа. Внешние `$ref` запрещены, если их цели отдельно не включены в grant и handoff.
3. При gate не обходить рекурсивно provenance, `backward_compatible_with`, source/derived_from handoff и отчёты старых шагов. Проверять все **прямые** required inputs и sequence gate. Provenance показывает происхождение нового самодостаточного экспорта, но не делает старые исходники дополнительным входом. Для documentation export допустимы `deployment_status: DOCS_PUBLISHED`, `deployed_environment: documentation`; это не статус runtime provider.
4. Если исторические digest относятся к CRLF-копиям, контроллер может добавить конечный блок `ARTIFACT_BYTE_BINDING:<id>:BEGIN/END` со статусом `VERIFIED`, точными handoff_id/version/producer_commit, consumers, списком path/historical_sha256/git_blob_sha256, evidence_report и единственной причиной `LF_CRLF_ONLY`. Это явное дополнение §1.4/§1.5 журнала, не изменение старых байтов и не новый API-релиз. Контроллер предварительно доказывает совпадение старых bytes, Git bytes и причину различия. FIX обязан указать этот binding ID в регистрации и промпте; проверять **сырые Git bytes** по git_blob_sha256, а исторические значения — на совпадение с исходным handoff. Нельзя хешировать декодированный/нормализованный текст, самостоятельно вычислять «новый правильный digest» или применять binding к иному prompt/commit/файлу. В отчёте фиксируются обе суммы и ID привязки. Отсутствие, дубликат, несовпадение или блок `ARTIFACT_BYTE_BINDING_REVOCATION:<id>:BEGIN/END` со статусом REVOKED блокируют gate.
5. Для новых пакетов digest всегда вычисляется по опубликованным Git/raw bytes. Два этапа публикации исключают самоссылку: A содержит артефакты, B — handoff/регистрацию/задание со ссылками на A. Commit B и подтверждение push передаются оператору отдельно, не записываются внутрь B. Формат DETACHED_V1 для runtime-отчёта остаётся без изменений.
6. Для составных schema-артефактов (multi-schema bundle, содержащих под `definitions` или `$defs` несколько моделей с локальными `$defs` и внутренними ссылками `#/$defs/...`), базой разрешения таких ссылок признаётся корень соответствующей модели, если контроллером нормативно установлено автономное использование вложенных схем. Проверка валидности схем и внутренних ссылок при contract gate проводится для каждой модели автономно (per-subschema). Отсутствие общего `$defs` на уровне внешнего контейнера не образует дефекта схемы при наличии валидного локального определения в модели.
