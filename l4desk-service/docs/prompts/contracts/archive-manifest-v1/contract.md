# Archive Manifest Contract v1 — Нормативный контракт архивных пакетов L4Desk

Версия документационного контракта: `1.0.0`.  
Producer step: `L4D-15A-DOCS` (`l4desk-service`).  
Основание каскада: принятый контракт `H-L4D-14-MB-v1` (шаг 28 MenuBuilder).  
Целевые потребители (Consumers): `L4D-15B-IOT`, `L4D-15C-MEDIA`, `L4D-16-MB`.  
Разделы архитектуры: 3, 5, 6, 7, 10, 13, 14, 15, 16, 17, 18.  
Scope: `l4desk-service` (изоляция: runtime-репозитории не открывать и не модифицировать).

---

## 1. Назначение и границы контракта

Настоящий контракт является общим, неизменяемым (immutable) нормативным стандартом создания, валидации, хранения, учёта и очистки (purge) помесячных архивных пакетов в экосистеме L4Desk.

Контракт обеспечивает:
1. Полную независимость реализации архивации в подсистемах IoT (`iot-rpc-rest-app`, шаг `L4D-15B-IOT`) и медиа (`l4media`, шаг `L4D-15C-MEDIA`).
2. Единый формат хранения данных на смонтированном томе архивов.
3. Гарантии целостности данных через криптографические контрольные суммы (SHA-256) и повторное контрольное перечитывание (full reread verification).
4. Защиту от преждевременного удаления данных через монотонный контроль курсоров потребителей (Consumer Cursor Guard).
5. Абсолютную сохранность финансового ядра, агрегатов и итоговых данных сессий (No-Financial-Purge Invariant).
6. Соблюдение установленных сроков хранения: 3 полных календарных месяца в горячей оперативной БД и не менее 3 лет в архивном хранилище с обязательным включением в план резервного копирования (Backup Invariant).

## 2. Состав контрактного пакета

Пакет спецификации размещён в каталоге `l4desk-service/docs/prompts/contracts/archive-manifest-v1/` и включает:
- `contract.md` — настоящая полная нормативная спецификация.
- `archive-manifest.schema.json` — строгая JSON-схема манифеста (`manifest.json`) по стандарту JSON Schema Draft 2020-12.
- `schemas.json` — сводный пакет определений `$defs`: `ArchiveManifest`, `FileEntry`, `RecordEnvelope`, `VerificationResult`, `PurgeResult`, `ArchiveError`, `RetentionPolicy`, `StorageLayout`.
- `examples.json` — канонические golden-фикстуры (IoT, Media, MenuBuilder) и негативные приёмочные векторы (Acceptance Vectors), проверяющие срабатывание защитных барьеров.
- `validate_archive_manifest.py` — исполняемый тестовый раннер валидации схем и векторов.
- `verification.md` — доказательная база верификации и побайтовые хеши SHA-256.

Все ссылки внутри пакета локальны, внешние сетевые `$ref` запрещены.

## 3. Сквозные идентификаторы архивации (Archive Identifiers)

Контракт опирается на схему данных `shared/etranprocessing_db` (модель `FinArchiveBatch`, таблица `fin_archive_batches`, ревизия миграции `027`) и принятые в Хабе идентификаторы:

| Идентификатор | Тип и ограничения | Семантика и назначение |
|---|---|---|
| `archive_batch_id` | `String(128)`, паттерн `^[a-z0-9_-]{8,128}$` | Глобально уникальный идентификатор архивного пакета (например, `arch-iot-2026-05-b91c84f2`). Первичный ключ батча. |
| `owner_project` / `source_project` | `String(64)`, enum: `iot-rpc-rest-app`, `l4media`, `MenuBuilder` | Проект-владелец архивируемых записей. Второй компонент составного первичного ключа в таблице `fin_archive_batches` (`id`, `source_project`). |
| `source_month` / `archive_month` | `String(7)`, паттерн `^[0-9]{4}-(0[1-9]\|1[0-2])$` | Календарный закрытый месяц данных (`YYYY-MM`). В БД мапится в `Date` первого числа месяца. |
| `cursor` | `BigInteger >= 0` | Порядковый номер (offset/id) в потоке событий источника (`inbox.event_id`). |
| `through_cursor` | `BigInteger >= 0` | Верхняя граница курсора источника, включённая в данный архивный пакет. |
| `consumers_passed_cursor` | `BigInteger >= 0` | Подтверждённый курсор обязательных внешних потребителей (например, воркера суточного биллинга MenuBuilder `FinUsageDaily`). |
| `source_event_id` | `String(128)` | Непрозрачный идентификатор исходного события, сохраняемый в финансовом регистре без жёсткого foreign key к удаляемым деталям. |
| `source_events_hash` | `String(64)` | Хеш SHA-256 группы исходных событий, удостоверяющий расчет суточного использования или сверки. |

## 4. Архитектура размещения на томе (Storage Volume Layout)

### 4.1. Канонический путь архивного пакета
Каждый сформированный и проверенный архивный пакет размещается по фиксированному пути относительно точки монтирования тома:

```text
<volume_root>/<year>/<month>/<project>/<archive_batch_id>/
  ├── data.jsonl.gz       (или именованные партиции: events.jsonl.gz, samples.jsonl.gz)
  ├── manifest.json       (канонический манифест пакета)
  └── checksum.sha256     (контрольные суммы всех файлов пакета)
```

Пример:
`/mnt/l4desk-archive/2026/05/iot-rpc-rest-app/arch-iot-2026-05-b91c84f2/`

### 4.2. Атомарный жизненный цикл каталога (Temporary Staging & Atomic Rename)
Для исключения появления неполных, повреждённых или недописанных пакетов в основном дереве архива строго предписывается следующий порядок файловых операций:

1. **Размещение staging-каталога на том же физическом томе**:  
   Временный каталог обязан создаваться внутри того же файлового монтирования (`<volume_root>/<year>/<month>/<project>/.tmp_<archive_batch_id>_<timestamp>/`), чтобы обеспечить атомарность операции переименования на уровне ядра ОС (`rename(2)` / `os.replace`). Перемещение между разными файловыми системами запрещено.
2. **Потоковая запись и сброс на диск**:  
   Все данные пакета (`data.jsonl.gz`) записываются во временный каталог. Перед переходом к верификации вызывается принудительный сброс буферов операционной системы (`fsync`) и закрытие файловых дескрипторов.
3. **Расчёт контрольных сумм и создание манифеста**:  
   Вычисляется SHA-256 каждого файла данных, формируется `manifest.json` в состоянии `prepared`, создаётся файл `checksum.sha256`.
4. **Контрольное перечитывание и проверка выборки**:  
   Выполняется полный reread файлов из временного каталога (см. Раздел 6).
5. **Атомарное переименование**:  
   После успешной верификации временный каталог переименовывается в целевой `<archive_batch_id>`. Только после этого манифест переходит в состояние `verified`.
6. **Защита от сбоев**:  
   При возникновении ошибки на этапе записи или верификации временный каталог удаляется, либо помечается суффиксом `.failed_<timestamp>`, статус пакета фиксируется как `failed`, а горячие данные в БД не модифицируются.

## 5. Формат данных MVP и каноническая сериализация

### 5.1. Формат файлов данных
- **Формат контейнера**: Gzip-сжатый UTF-8 JSON Lines (`JSONL.gz`).
- **Структура строк**: Ровно один валидный JSON-объект на строку, завершаемый символом LF (`\n`, байт `0x0A`).
- **Отсутствие BOM**: Использование UTF-8 BOM (`0xEF, 0xBB, 0xBF`) запрещено.

### 5.2. Детерминизм сериализации JSON
Для обеспечения повторяемости вычисления контрольных сумм:
1. Ключи JSON-объектов сортируются лексикографически (`sort_keys=True`).
2. Разделители форматируются компактно без лишних пробелов (`separators=(',', ':')`).
3. Символы Unicode экранируются стандартным образом либо передаются в чистом UTF-8 без искажения (`ensure_ascii=False`).
4. Временные метки сериализуются в строгом формате ISO 8601 UTC с суффиксом `Z` (например, `2026-05-15T12:00:00Z` или с микросекундами).
5. Числовые значения с плавающей точкой (`float`) в коммерческих и финансовых полях категорически запрещены — используются исключительно целые копейки (`BigInteger`).

### 5.3. Детерминизм сжатия Gzip
Стандартный заголовок Gzip содержит временную метку `mtime`. Для обеспечения побайтовой идентичности при повторном экспорте одинаковых данных воркер обязан фиксировать `mtime=0` (эпоха Unix) при создании архива через `gzip.GzipFile(..., mtime=0)`.

### 5.4. Файл контрольных сумм `checksum.sha256`
Файл формируется в стандартном формате утилиты `sha256sum`:
```text
<sha256_файла_данных>  data.jsonl.gz
<sha256_манифеста>  manifest.json
```
Два пробела между хешем и именем файла обязательны.

## 6. Жизненный цикл пакета и машина состояний (State Machine)

Манифест архивного пакета проходит строгую конечную последовательность состояний:

```text
[ Выборка закрытого месяца > 3 мес ]
                 │
                 ▼
          ┌─────────────┐
          │  PREPARED   │ ──(Ошибка записи/диска)──► [ FAILED ]
          └─────────────┘
                 │
  [ Full reread + SHA-256 + Count match ]
  [ Sample restore passed + Cursor checked ]
  [ Atomic rename .tmp_* -> target ]
                 │
                 ▼
          ┌─────────────┐
          │  VERIFIED   │ ──(Ошибка БД при purge)──► [ FAILED / RETRY ]
          └─────────────┘
                 │
  [ Bounded chunked purge hot DB details ]
                 │
                 ▼
          ┌─────────────┐
          │   PURGED    │
          └─────────────┘
```

1. **`prepared`**:  
   Пакет экспортирован во временный каталог, файлы засинхронизированы на диск (`fsync`). Поле `verification` равно `null` или содержит промежуточный статус.
2. **`verified`**:  
   Выполнено полное перечитывание файлов данных с распаковкой потока, совпало количество строк (`reread_records_count == total_records`), совпал SHA-256 (`reread_checksum_sha256 == sha256`), пробная выборка записей успешно восстановлена (`restore_sample_status == "passed"`), курсор потребителей проверен (`cursor_guard_passed == true`), временный каталог атомарно переименован.
3. **`purged`**:  
   Горячие технические детали в оперативной БД удалены до границы `through_cursor` / `max_occurred_at`. Поле `purge` заполнено датой и количеством удалённых строк.
4. **`failed`**:  
   Обнаружена ошибка целостности, сбой диска, отставание курсора или сбой выборки. Поле `error` обязательно заполнено кодом и описанием ошибки. **Очистка БД категорически заблокирована**.

## 7. Барьеры безопасности очистки (Purge Safety Guards & Invariants)

### 7.1. Обязательные условия для разрешения Purge
Операция удаления данных из оперативной БД разрешена **только и исключительно** при одновременном выполнении всех условий:
1. Статус пакета в манифесте равен `verified`.
2. Поле `verification.verified_at_utc` заполнено валидной датой.
3. Контрольная сумма перечитанных файлов побайтово совпадает с первоначальным расчётом.
4. Количество перечитанных строк точно совпадает с экспортированным.
5. Пробное восстановление (sample restore) из архива декодировало записи без ошибок схемы.
6. **Consumer Cursor Guard**: Если у архивируемых данных есть связанный курсор (`through_cursor`), то значение `consumers_passed_cursor` обязано быть строго больше или равно `through_cursor` (`consumers_passed_cursor >= through_cursor`). Если хотя бы один обязательный потребитель (воркер суточного использования, сверка) не подтвердил продвижение своего курсора, удаление блокируется.
7. В целевом временном окне отсутствуют активные незавершённые или переоткрытые сессии (`active/reopened records`).

### 7.2. Список сущностей, категорически исключённых из Purge (No-Financial-Purge)
Массовая очистка технических деталей никогда не затрагивает:
- Таблицы финансового сабледжера (`fin_ledger_transactions`, `fin_ledger_entries`).
- Таблицы платежей (`fin_payments`, `fin_manual_payments`).
- Тарифные планы и биллинговые циклы (`fin_tariff_versions`, `fin_billing_cycles`).
- Суточные и месячные начисления и агрегаты (`fin_usage_daily`, `fin_terminal_monthly_charges`).
- Проекции балансов (`fin_balance_projections`).
- Итоговые строки сессий (`l4desk_sessions`).
- Результаты прогонов финансовой сверки (`fin_reconciliation_runs`).
- Реестр архивных пакетов (`fin_archive_batches`).
- Хеши исходных событий (`source_events_hash`), используемые в сквозном аудите Хаба.

### 7.3. Ограниченное порционное удаление (Bounded Chunked Purge)
Удаление строк из БД выполняется ограниченными порциями (чанками по 500–1000 строк) в отдельных транзакциях для предотвращения блокировок таблиц, разрастания WAL и таймаутов соединений.

## 8. Политика сроков хранения и резервного копирования (Retention & Backup)

### 8.1. Горячее окно хранения (Hot Retention)
- **Срок**: Ровно 3 полных закрытых календарных месяца.
- **Правило вычисления**:  
  Если текущая дата — сентябрь 2026 года (2026-09-21), то тремя полными закрытыми месяцами являются август (2026-08), июль (2026-07) и июнь (2026-06). Ближайшим закрытым месяцем, разрешённым к архивированию и очистке, является **май 2026 года** (`2026-05`) и более ранние месяцы. Попытка архивировать или удалить данные за июнь 2026 года или позже должна немедленно отклоняться с ошибкой `HOT_RETENTION_VIOLATION`.

### 8.2. Архивное хранение (Archive Retention)
- **Срок**: Не менее 3 полных лет с момента создания пакета (`retain_until >= created_at + 3 years`).
- До истечения срока `retain_until` удаление файлов архива с тома категорически запрещено.

### 8.3. Резервное копирование смонтированного тома (Backup Invariant)
- Смонтированный том `<volume_root>` обязан входить в корпоративную схему регулярного резервного копирования (холодные снапшоты, S3 Cold Storage, offsite replication).
- Простое нахождение файла на локальном диске хоста **не признаётся** резервной копией.
- Перед запуском архивации воркер обязан проверить доступность тома на запись; при недоступности тома процесс завершается ошибкой `VOLUME_UNAVAILABLE`, горячие данные в БД остаются нетронутыми.

## 9. Коды ошибок архивации (Error Codes)

При возникновении сбоев манифест фиксирует ошибку в объекте `error` со следующими стандартизированными кодами:

| Код ошибки | Описание причины сбоя |
|---|---|
| `CHECKSUM_MISMATCH` | Хеш SHA-256 файла при повторном перечитывании не совпал с исходным хешем. |
| `COUNT_MISMATCH` | Число строк при перечитывании отличается от заявленного `total_records`. |
| `CURSOR_LAG_DETECTED` | Курсор обязательных потребителей (`consumers_passed_cursor`) меньше архивной границы (`through_cursor`). |
| `RESTORE_SAMPLE_FAILED` | Ошибка распаковки или валидации пробной выборки записей из архива. |
| `HOT_RETENTION_VIOLATION` | Попытка архивации данных моложе трёх полных закрытых месяцев. |
| `DISK_SPACE_EXHAUSTED` | Недостаточно свободного дискового пространства на смонтированном томе. |
| `VOLUME_UNAVAILABLE` | Смонтированный том недоступен или смонтирован в режиме read-only. |
| `ACTIVE_RECORDS_DETECTED` | В архивируемом периоде обнаружены активные или незавершённые сессии. |
| `ATOMIC_RENAME_FAILED` | Ошибка атомарного перемещения каталога из staging в целевой путь. |
| `PURGE_OPERATION_FAILED` | Ошибка транзакции базы данных при удалении горячих записей. |
