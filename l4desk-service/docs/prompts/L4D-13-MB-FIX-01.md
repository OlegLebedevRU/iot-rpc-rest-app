## 1. Цель

Исправить L4Desk onboarding и навигацию в пределах проекта `MenuBuilder`.

В L4Desk должен быть корневой раздел **«Терминалы»**, расположенный выше раздела «Видеонаблюдение». Он становится единственной пользовательской точкой для списка терминалов, создания терминала, подключения Агента, отображения PIN/readiness и перехода к консоли или видеонаблюдению.

Создание терминала в L4Desk должно переиспользовать существующий канонический backend-сценарий создания терминала административного контура `menubuilder.admin/terminals`.

Пользователь не должен вводить, выбирать, редактировать или самостоятельно придумывать:

- серийный номер;
- `device_id`;
- алгоритм или формат серийного номера.

Серийный номер и `device_id` выдаются сервером по существующим правилам административного создания терминала и отображаются в L4Desk только в режиме чтения.

## 4. Единый канонический сценарий создания терминала

В `MenuBuilder` должен быть один server-side domain use case создания terminal business record.

Его обязаны использовать:

1. административный контур создания терминала;
2. L4Desk onboarding;
3. корневой раздел «Терминалы».

Если текущая административная логика находится внутри route handler, разрешается выделить её в общий сервис. Поведение административного контура должно сохраниться, кроме необходимой корректировки диапазона выдаваемых новых `device_id`.

Общий use case обязан:

1. Валидировать tenant/organization scope, права и actor.
2. Создавать terminal business record в существующих транзакционных границах.
3. Выделять новый `device_id` только в диапазоне от `1000001` до `1999999` включительно.
4. Формировать SN по существующей канонической формуле административного сценария.
5. Проверять уникальность SN и `device_id`.
6. Сохранять actor, audit и correlation/operation identifier по текущим правилам проекта.
7. Возвращать неизменяемые идентификаторы созданного терминала.
8. Не создавать второй терминал при идемпотентном повторе одной L4Desk-операции.

Новые `device_id` вида `10000005` недопустимы.

Allocator должен быть безопасен при параллельных запросах. Нужно использовать существующий корректный механизм либо усилить его в пределах `MenuBuilder`, не создавая вероятность выдачи одного ID двум терминалам.

Если в базе есть legacy-записи вне диапазона:

- не изменять их в рамках данного prompt;
- не нарушать их связь с SN, сертификатами, provisioning или Агентами;
- применять новый диапазон только к новым терминалам;
- отразить в отчёте только безопасную агрегированную информацию;
- отдельно указать необходимость migration prompt, если она действительно подтверждена.

## 5. Серийный номер и provisioning

SN — системный неизменяемый идентификатор.

Обязательные правила:

- пользователь не вводит SN;
- пользователь не редактирует SN;
- frontend не рассчитывает SN;
- L4Desk не имеет собственной формулы SN;
- административный и L4Desk-потоки используют одну каноническую формулу;
- SN отображается только после успешного ответа backend;
- SN допускается копировать, но не изменять.

После успешного создания terminal business record L4Desk запускает существующий provisioning/PIN flow.

В provisioning передаются идентификаторы, выданные общим use case:

- `terminal_id`;
- `device_id`;
- `serial_number`;
- `operation_id` или `correlation_id`;
- tenant identifier.

Provisioning не должен создавать второй terminal business record или менять уже выданные SN и `device_id`.

Если provisioning/PIN завершается ошибкой:

- созданный terminal business record сохраняется;
- SN и `device_id` сохраняются неизменными;
- UI показывает понятное состояние ошибки;
- повтор используется в рамках существующей идемпотентной модели.

Если существует прежний опубликованный L4Desk URL раздела терминалов внутри настроек:

- сохранить обратную совместимость через redirect на новый корневой маршрут;
- не допустить обход tenant scope через redirect;
- не менять поведение classic profile, если старый маршрут относится к classic UX.

Корневой раздел «Терминалы» должен предоставлять:

- список терминалов текущего tenant;
- отображение статуса терминала;

## 8. Корректировка мастера подключения

Действие **«Мастер подключения терминала L4Desk»** необходимо перенести из «Консоли» в раздел «Терминалы».

Консоль должна работать только с уже созданными терминалами. При отсутствии терминалов она должна показать понятный CTA с переходом в «Терминалы».

Мастер первого подключения открывается из «Терминалов», включая автоматическое открытие после регистрации, если такой сценарий уже предусмотрен L4Desk flow.

На шаге создания пользователь может вводить только разрешённые бизнес-поля:

- название терминала;
- адрес или место установки;
- примечание;
- timezone, если он необходим текущей модели.

На форме не должно быть:

- editable input для SN;
- editable input для `device_id`;
- выбора формата SN;
- текста, предлагающего пользователю придумать серийный номер.

После успешного создания мастер показывает системные значения в read-only виде:

- SN;
- `device_id`, если он нужен в UX;
- статус создания;
- статус provisioning;
- PIN и срок действия в существующей модели;
- readiness states.

Последовательность мастера должна оставаться следующей:

1. Создать терминал.
2. Получить и показать PIN.
3. Скачать и установить Агент.
4. Дождаться сертификата и online.
5. Открыть консоль или видеонаблюдение.

Не менять правила PIN, сертификатов, readiness и entitlement за пределами интеграции с общим terminal creation use case.

## 9. API и совместимость

Не ломать существующие административные API создания терминалов.

Если для L4Desk нужен отдельный API endpoint:

- он обязан вызывать общий domain service;
- он не должен дублировать алгоритм создания;
- request DTO не принимает пользовательские `serial_number` и `device_id`;
- response DTO возвращает созданные системой идентификаторы и состояние, необходимое для read-only UI и provisioning.

Если старый L4Desk request ранее содержал пользовательский SN:

- не использовать его для создания канонического идентификатора;
- обработать согласно существующей compatibility policy;
- не допускать silent override канонического SN.

Не изменять IoT contract. При необходимости такого изменения завершить prompt как `BLOCKED_EXTERNAL_CONTRACT`.

## 11. Критерии приёмки

Prompt принимается только при одновременном выполнении условий:

1. «Терминалы» — первый корневой раздел L4Desk.
