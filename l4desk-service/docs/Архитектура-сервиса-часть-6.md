### Итерация 6 — резюме взаимопонимания

- До первой успешной оплаты работает только бесплатный пакет: первый терминал и общие `120 минут/сутки` консоли и видео. Трёхдневной отсрочки до первой оплаты нет.
- ЮKassa пополняет внутренний баланс на выбранную пользователем целую сумму в рублях. Первая успешная оплата создаёт индивидуальный якорь расчётного цикла.
- Контракт `MenuBuilder ↔ iot-rpc-rest-app` строится через версионированный internal REST API и восстанавливаемый event feed с cursor.
- Внутренние RabbitMQ/MQTT-топики остаются ответственностью `iot-rpc-rest-app`.
- Существующие контракты Агента из `tools` должны оставаться обратно совместимыми.
- Существующие и новые пользователи должны работать с одними реализациями консоли, видеонаблюдения и удалённого управления; коммерциализация добавляется политикой доступа и учётом, а не вторым техническим контуром.
- Первые клиенты — физлица через ЮKassa. Для юрлиц на первом этапе superuser вручную регистрирует подтверждённый факт оплаты.
- История должна поддерживать пакетную помесячную архивацию, но финансовые регистры нельзя бездумно удалять через три месяца.

### Что уже есть для единого console/video-контура

Проверка текущей реализации подтверждает, что основа уже достаточно зрелая:

- `MenuBuilder/backend/app/services/iot_client.py` содержит вызовы `iot-rpc-rest-app` для:
  - получения статуса remote input;
  - выдачи и освобождения lease;
  - смены scope;
  - запуска и остановки stream;
  - keepalive;
  - клавиатуры, мыши и shortcut;
  - WebSocket remote-input;
- `MenuBuilder/backend/app/routers/video_control.py` и набор `test_video_control.py`, `test_step4_video_contracts.py`, `test_video_stream_permissions.py` уже закрепляют video flow;
- `tools/leo4proxy` поддерживает существующие диагностические RPC-команды:
  - `7000 CMD_DIAG_STREAM_CONTROL`;
  - `7001 EXEC`;
  - `7002 CANCEL`;
- текущий MQTT/RPC lifecycle `tsk → req → rsp → res → cmt` уже документирован и реализован в `iot-rpc-rest-app`.

Следовательно, не нужно создавать новые «платную консоль» и «платное видео». Нужно обернуть существующие use cases общей коммерческой политикой.

### Единая реализация для старой и новой концепции `MenuBuilder`

Предлагаемая структура:

```text
Текущий пользователь MenuBuilder ─┐
                                  ├─→ единый RemoteSessionUseCase
Новый user role=5 ────────────────┘       │
                                          ├─ tenant access policy
                                          ├─ fin entitlement policy
                                          ├─ IoT session adapter
                                          └─ l4media orchestration
```

Различаться должны только:

- меню и доступные разделы;
- tenant scope;
- необходимость коммерческой entitlement-проверки;
- отображение баланса, квоты и причин блокировки.

Одинаковыми остаются:

- API запуска/остановки;
- lease и session state;
- IoT/MQTT/RPC transport;
- video player;
- keyboard/mouse/console protocol;
- обработка ошибок и cleanup;
- тесты базового поведения.

На frontend лучше сохранить один набор React-компонентов и route-level экранов. Новый сервис получает другой navigation profile, но не копию страниц. На backend существующие handlers вызывают общий use case; entitlement добавляется как policy/dependency перед фактическим стартом.

### Обратная совместимость с Агентом `tools`

Граница совместимости должна быть двухступенчатой:

```text
MenuBuilder contract vN
        ↕
iot-rpc-rest-app adapter
        ↕
Agent contract v1: topics + method_code + payload
```

Новые финансовые поля не должны попадать в MQTT payload Агента. Агенту не нужно знать о balance, tenant billing cycle или ЮKassa. Он получает только прежнюю техническую команду запуска/остановки.

#### Правила совместимости

1. Существующие MQTT topics и значения `method_code` не переиспользуются для другого смысла.
2. Существующие обязательные поля payload не удаляются и не меняют тип.
3. Новые поля добавляются только как необязательные и лишь при реальной необходимости.
4. `iot-rpc-rest-app` адаптирует новый internal API к контракту конкретной версии Агента.
5. Версия и capabilities Агента фиксируются при presence/инвентаризации устройства.
6. Новая server-side функциональность не должна требовать немедленного обновления уже установленного Агента.
7. Golden vectors из `tools/leo4proxy/examples` становятся regression fixtures для `iot-rpc-rest-app`.
8. Перед релизом проверяются как минимум текущая опубликованная версия Агента и новая версия-кандидат.

Таким образом, контракт `MenuBuilder ↔ IoT` может развиваться быстрее, а Agent protocol остаётся стабильным.

### Платежи физлиц через ЮKassa

Для первого этапа достаточно:

- сумма пополнения — целое число рублей;
- email пользователя передаётся для платёжного/чекового flow;
- `return_url` используется только для UX;
- фактический `succeeded` подтверждается сервером;
- payment, webhook, fallback polling и ledger связаны через `provider_payment_id`;
- параметры чека, ставка НДС и предмет расчёта являются конфигурацией, а не hardcode.

Поскольку первые клиенты — физлица, интеграция должна предусмотреть данные чека ЮKassa. Конкретные фискальные настройки необходимо согласовать с юридической/бухгалтерской моделью сервиса, но для архитектуры достаточно сохранить в `fin_payments` идентификаторы payment и receipt, сумму, статус и снимок отправленных позиций.

### Ручная регистрация оплаты юрлица

Superuser не должен напрямую менять `fin_balance_projection`. Вместо этого создаётся документ:

```text
fin_manual_payments
```

Обязательные поля:

- tenant;
- сумма в целых рублях;
- дата фактического поступления;
- номер/назначение банковского документа;
- плательщик;
- комментарий;
- user superuser, создавший запись;
- `created_at`;
- необязательное вложение или ссылка на подтверждение.

После проведения документ создаёт обычную двойную проводку, как платёж ЮKassa. Изменять проведённый документ нельзя; ошибка исправляется сторно и новым документом. Поэтому автоматические и ручные оплаты одинаково участвуют в балансе и сверках.

### Стратегия хранения и архивации

Рекомендую разделить данные на три класса.

#### Класс A — финансовое ядро

```text
fin_ledger_transactions
fin_ledger_entries
fin_payments
fin_manual_payments
fin_billing_cycles
fin_balance_projections
```

Эти данные небольшие по объёму и нужны для аудита. Их не следует удалять из основной БД через три месяца. Для MVP рациональнее хранить их online длительно, а затем установить юридически подтверждённый срок хранения.

#### Класс B — расчётные агрегаты

```text
fin_usage_daily
fin_terminal_monthly_charges
fin_notification_deliveries
```

Их также желательно оставить online: именно они объясняют баланс. Объём — одна или несколько строк на terminal/day, поэтому нагрузка умеренная.

#### Класс C — высокообъёмная техническая история

```text
IoT session events
RPC transitions
heartbeat/presence history
l4media technical samples
application audit logs
```

Именно эти данные целесообразно архивировать помесячно после `3 месяцев` горячего хранения.

### Пакетная помесячная архивация

```text
Каждый месяц M:
  1. Выбрать закрытые данные старше 3 полных календарных месяцев.
  2. Создать общий archive_batch_id для месяца-источника.
  3. Каждый проект экспортирует только принадлежащие ему сущности.
  4. Сформировать manifest: row count, min/max timestamps, checksum.
  5. Проверить чтение и checksum архива.
  6. Пометить batch как verified.
  7. Только после verification удалить/отсоединить горячие детали.
```

Из-за раздельных БД `MenuBuilder` и `iot-rpc-rest-app` это не одна распределённая транзакция. Общность обеспечивается `archive_batch_id`, месяцем и manifest каждого владельца.

Минимальный формат — сжатый `JSONL` или `Parquet` плюс manifest. Для MVP `JSONL.gz` проще в диагностике; `Parquet` полезнее позже для больших объёмов и аналитики.

### Что остаётся в горячей БД после архивации

- финансовый ledger и balance;
- суточные/месячные финансовые агрегаты;
- итог сессии: начало, конец, длительность, тип и сумма;
- `source_events_hash`;
- archive manifest и расположение пакета;
- последние три месяца подробных IoT/RPC-событий.

Технический event feed, ещё не импортированный `MenuBuilder`, архивировать нельзя. Сначала cursor всех обязательных потребителей должен пройти архивируемую границу.

### Защита ссылок на архив

Финансовая строка не должна иметь обязательный FK на техническое событие, которое будет удалено из горячей БД. Вместо этого сохраняются:

- внешний `source_event_id`;
- `source_project`;
- `source_events_hash`;
- `archive_batch_id` после архивации.

Это позволяет подтвердить происхождение начисления, не удерживая все heartbeat/RPC transitions в основной БД.

### Идеи без расширения MVP

- В Хабе показывать статус архивного пакета: `prepared`, `verified`, `purged`, `failed`.
- Подробные архивные данные сначала предоставлять как скачиваемый пакет superuser, без прозрачных SQL-запросов по архиву.
- Добавить страницу совместимости Агентов: version, capabilities, число устройств и дата последнего использования.
- Для нового navigation profile не создавать отдельный frontend build — использовать feature/product profile в одной SPA.

### Три вопроса для уточнения

1. В модели внутреннего баланса правильно ли считать, что граница индивидуального цикла сама по себе не требует отдельной «покупки лицензии»: terminal-month начисляется при первом online терминала в новом цикле, usage — по суткам, а grace начинается только тогда, когда проведённое начисление впервые делает баланс отрицательным? Email `-7/-3/-1` тогда содержит прогноз следующего цикла и рекомендацию пополнить баланс.

2. Для ручной оплаты юрлица достаточно одного superuser, который создаёт неизменяемый документ с подтверждением и при ошибке делает сторно, или требуется согласование вторым superuser? Для MVP рекомендую первый вариант с полным audit trail.

3. Подтверждаете ли стратегию архивации: финансовое ядро и расчётные агрегаты остаются online, а после трёх полных месяцев пакетно архивируются главным образом подробные IoT/RPC/media-события; удаление горячих деталей разрешается только после manifest/checksum verification и прохождения consumer cursor?
