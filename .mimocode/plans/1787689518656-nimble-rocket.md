```python
@classmethod
async def get_devices_with_known_connect_state(
    cls, session: AsyncSession, max_age_seconds: int = 600
) -> set[str]:
    """Return client_ids where at least one of app_connect/svc_connect is NOT NULL
    AND details IS NOT NULL AND checked_at is within max_age_seconds."""
    from datetime import datetime, timedelta, timezone
    cutoff = datetime.now(timezone.utc) - timedelta(seconds=max_age_seconds)
    stmt = (
        select(DeviceConnection.client_id)
        .where(
            (DeviceConnection.app_connect.isnot(None) | DeviceConnection.svc_connect.isnot(None)),
            DeviceConnection.details.isnot(None),
            DeviceConnection.checked_at > cutoff,
        )
    )
    result = await session.execute(stmt)
    return set(result.scalars().all())
```

**Файл:** `app-service/core/services/devices.py`

Изменить `update_device_connections()`:

```python
@classmethod
async def update_device_connections(cls, session: AsyncSession):
    list_devices = await DeviceRepo.list(session)

    # 1. Определяем устройства с известным состоянием — исключаем из запроса к API
    known_sn_set = await DeviceRepo.get_devices_with_known_connect_state(session)
    sn_to_poll = [sn for sn in list_devices if sn not in known_sn_set]

    # 2. Запрашиваем RabbitMQ API только для устройств без известного состояния
    dev_online = await RmqAdmin.get_online_devices(sn_to_poll) or []
    dev_statuses = [
        DeviceConnectStatus(
            client_id=d.user,
            connected_at=d.connected_at,
            last_checked_result=True,
            device_id=0,
            details=d,
        )
        for d in dev_online
    ]

    # 3. СНАЧАЛА вычисляем last_checked_result из флагов для ВСЕХ устройств
    #    (для "известных" устройств это даст корректное значение из app_connect/svc_connect)
    await DeviceRepo.compute_last_checked_from_flags(session, list_devices)

    # 4. ПОТОМ сбрасываем флаги ТОЛЬКО для опрошенных устройств
    #    (перезапишет формулу для устройств, которые мы опрашиваем через API)
    await DeviceRepo.reset_connection_flag(session, sn_to_poll)

    # 5. Обновляем онлайн-устройства из результатов API
    await DeviceRepo.update_connections(session, dev_statuses)

    await session.commit()
```

**Важно о порядке операций:**
- Шаг 3 (формула) идёт ПЕРЕД шагом 4 (сброс), чтобы устройства с известными флагами получили `last_checked_result` из формулы, а не были обнулены.
- Шаг 4 (сброс) применяется ТОЛЬКО к `sn_to_poll` — устройствам, которые мы реально опрашиваем через API.
- Шаг 5 (обновление из API) перезаписывает `last_checked_result = True` только для онлайн-устройств из `sn_to_poll`.
- Итог: "известные" устройства получают значение из формулы, остальные — из RabbitMQ API.

## 7. Вычисление last_checked_result из флагов

**Файл:** `app-service/core/crud/device_repo.py`

Добавить метод:

```python
@classmethod
async def compute_last_checked_from_flags(
    cls, session: AsyncSession, sn_arr: list[str]
):
    """Set last_checked_result = COALESCE(app_connect, false) OR COALESCE(svc_connect, false)
    for all devices in sn_arr."""
    if not sn_arr:
        return
    stmt = text("""
        UPDATE tb_device_connections
        SET last_checked_result = COALESCE(app_connect, false) OR COALESCE(svc_connect, false)
        WHERE client_id = ANY(:sn_arr)
    """)
    await session.execute(stmt, {"sn_arr": sn_arr})
```

**Важно:** Этот вызов идёт ПЕРЕД `reset_connection_flag()` и `update_connections()`, поэтому:
- Устройства с известными флагами (исключённые из поллинга) получат `last_checked_result` на основе формулы — это их окончательное значение.
- Устройства без флагов (оба NULL) получат `last_checked_result = false OR false = false` — но это будет перезаписано на шагах reset + update для опрашиваемых устройств.
- Устройства, найденные в RabbitMQ API, получат `last_checked_result = True` из `update_connections()` — формула будет перезаписана.

## A1. Архитектура проекта

**Стек:** FastAPI + FastStream (RabbitMQ) + SQLAlchemy 2.0 (async) + PostgreSQL + RabbitMQ с MQTT-плагином.

**Точка входа:** `app-service/run_main.py` → `app-service/main.py` → `app-service/create_api_app.py` (фабрика приложения).

**Lifespan startup sequence:**
1. `_start_broker_with_retry()` — подключение к RabbitMQ с exponential backoff
2. `declare_x_q()` — идемпотентная декларация всех exchanges, queues, bindings
3. `_sync_rmq_device_definitions_on_startup()` — синхронизация MQTT-пользователей/ACL из БД в RabbitMQ (с PG advisory lock)
4. Запуск topology watchdog (периодическая перe-декларация топологии)
5. Запуск APScheduler с двумя job'ами (TTL decrement + billing)

**Модуль подписчиков** регистрируется через `importlib.import_module()` в `_ensure_rabbit_subscribers_registered()` — декораторы `@fs_router.subscriber` исполняются при импорте.

Два модуля подписчиков:
- `core.topologys.fs_queues` — device-facing очереди (evt, ack, req, res, out)
- `core.topologys.internal_bus` — internal очереди (core_jobs, rmq_api_client_action, webhook_action, billing_counter_action)

## A6. MQTT-топики и ACL

### Формат топиков
- Устройство → Сервер: `dev/{SN}/{suffix}` (req, ack, evt, res, out)
- Сервер → Устройство: `srv/{SN}/{suffix}` (tsk, rsp, cmt, eva)

### Topic permissions (rmq_admin_api.py:61-66)
```python
{
    "exchange": "amq.topic",
    "write": "^dev.{client_id}.*",   # устройство может ПУБЛИКОВАТЬ в dev/{SN}/*
    "read": "^srv.{client_id}.*"     # устройство может ПОДПИСЫВАТЬСЯ на srv/{SN}/*
}
```

**Важно:** Паттерн `^dev.{client_id}.*` уже покрывает `dev/{SN}/app` и `dev/{SN}/svc` — никаких изменений в ACL не требуется.

### RabbitMQ MQTT plugin (rabbitmq.conf)
- MQTT over TLS на порту 8883
- `mqtt.ssl_cert_login = true` — SN устройства берётся из CN TLS-сертификата
- `mqtt.exchange = amq.topic` — все MQTT-сообщения идут в amq.topic

## A7. Анализ задачи — детали реализации

### 7.1. Парсинг тела сообщения

Устройства будут публировать в MQTT-топик `dev/{SN}/app` строку `"app_online"` или `"app_offline"`, и в `dev/{SN}/svc` строку `"svc_online"` или `"svc_offline"`.

Тело сообщения приходит как bytes. Нужно:
```python
body = msg.body.decode().strip().strip('"')
```
- `.decode()` — bytes → str
- `.strip()` — убрать пробелы/переносы
- `.strip('"')` — убрать кавычки если payload обёрнут в JSON-строку

### 7.2. Извлечение SN

Существующий `sn_getter_dep` (fs_depends.py:33) делает `routing_key[4:-4]`:
- `dev.ABC123.app` → `[4:-4]` → `ABC123` ✓ (суффикс `.app` = 4 символа)
- `dev.ABC123.svc` → `[4:-4]` → `ABC123` ✓ (суффикс `.svc` = 4 символа)

Существующие суффиксы тоже по 4 символа: `.ack`, `.req`, `.evt`, `.res`, `.out` — всё совместимо.

### 7.3. Стратегия оптимизации поллинга

**Текущая проблема:** `get_connection(sn_arr)` делает N HTTP-запросов к RabbitMQ Management API (по одному на каждое устройство). При тысячах устройств это создаёт значительную нагрузку.

**Решение:** Исключить из `sn_arr` устройства, для которых:
1. Хотя бы одно из полей `app_connect`/`svc_connect` != NULL (т.е. устройство отправляло статус)
2. `details` IS NOT NULL (т.е. были получены детали подключения ранее)
3. `checked_at` > (now() - 600 секунд) (т.е. проверка была недавно)

**Обоснование:** Если устройство активно отправляет статус через MQTT-топики, его состояние связи известно и не требует поллинга через Management API. Порог 600 секунд (10 минут) даёт запас на случай временной потери MQTT-сообщений.

**Ограничение:** RabbitMQ Management API `GET api/connections/username/{SN}` не поддерживает batch-запросы или фильтрацию по нескольким пользователям. Поэтому исключение работает на уровне формирования списка `sn_arr` — мы просто не делаем запрос для исключённых SN.

### 7.4. Формула last_checked_result

```
last_checked_result = COALESCE(app_connect, false) OR COALESCE(svc_connect, false)
```

| app_connect | svc_connect | Результат |
|-------------|-------------|-----------|
| NULL | NULL | false (нет данных) |
| true | NULL | true |
| false | NULL | false |
| NULL | true | true |
| NULL | false | false |
| true | true | true |
| true | false | true |
| false | true | true |
| false | false | false |

**Смысл:** Устройство считается онлайн, если хотя бы один из компонентов (app или svc) подключён.

### 7.5. Порядок операций в update_device_connections

```
1. Получить все SN из БД
2. Определить "известные" устройства (с флагами, деталями, свежей проверкой)
3. Сформировать sn_to_poll = все - известные
4. Запросить RabbitMQ API только для sn_to_poll
5. Сбросить last_checked_result = False ТОЛЬКО для sn_to_poll
6. Обновить last_checked_result = True для онлайн-устройств из sn_to_poll
7. Вычислить last_checked_result = app_connect OR svc_connect для ВСЕХ устройств
8. Commit
```

**Ключевой момент:** Шаг 7 (вычисление формулы) идёт ПОСЛЕ шагов 5-6 и覆盖ывает `last_checked_result` для всех устройств. Это значит:
- Устройства из sn_to_poll, которые онлайн в RabbitMQ: шаг 6 поставил True, шаг 7 может перезаписать на `app_connect OR svc_connect`. Если устройство онлайн в RabbitMQ, но не отправляло app/svc статус (оба NULL), формула даст false. Это может быть проблемой!

**Решение:** Изменить порядок — сначала вычислить формулу, потом обновить из RabbitMQ:
```
1-4. (как выше)
5. Вычислить last_checked_result = app_connect OR svc_connect для ВСЕХ
6. Сбросить last_checked_result = False ТОЛЬКО для sn_to_poll (перезапишет формулу для опрашиваемых)
7. Обновить last_checked_result = True для онлайн-устройств из sn_to_poll
8. Commit
```

Так устройства с известными флагами получат значение из формулы, а устройства без флагов будут обработаны через RabbitMQ API как раньше.

## A8. Тестовые сценарии

### Сценарий 1: Новое устройство (оба флага NULL)
- Устройство провизионировано, но ни разу не отправляло app/svc статус
- `app_connect = NULL, svc_connect = NULL`
- Поллинг: устройство включается в sn_to_poll, опрашивается через RabbitMQ API
- Формула: `false OR false = false` → `last_checked_result` зависит только от RabbitMQ API

### Сценарий 2: Устройство отправило app_online
- `app_connect = true, svc_connect = NULL`
- Поллинг: устройство ИСКЛЮЧАЕТСЯ из sn_to_poll (если details != NULL и checked_at < 600s)
- Формула: `true OR false = true` → `last_checked_result = true`

### Сценарий 3: Устройство отправило app_offline + svc_offline
- `app_connect = false, svc_connect = false`
- Поллинг: устройство ИСКЛЮЧАЕТСЯ из sn_to_poll
- Формула: `false OR false = false` → `last_checked_result = false`

### Сценарий 4: Устройство отправило app_online, потом svc_offline
- `app_connect = true, svc_connect = false`
- Поллинг: устройство ИСКЛЮЧАЕТСЯ из sn_to_poll
- Формула: `true OR false = true` → `last_checked_result = true`

### Сценарий 5: Устройство с флагами, но checked_at > 600s назад
- `app_connect = true, svc_connect = NULL, checked_at = 15 минут назад`
- Поллинг: устройство ВКЛЮЧАЕТСЯ в sn_to_poll (checked_at устарел)
- Формула: `true OR false = true` → `last_checked_result = true` (до перезаписи из RabbitMQ)
- После RabbitMQ: если устройство онлайн → `last_checked_result = true`, если оффлайн → `false`

### Сценарий 6: Устройство удалено/депровизионировано
- Устройство удалено из БД → DeviceConnection тоже удалён (cascade)
- Нет записи → нет запроса к API → нет проблемы
